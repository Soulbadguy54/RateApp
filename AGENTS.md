# Rate APP — инструкция для новых чатов и coding-агентов

**Назначение:** быстро восстанавливать проверенный контекст Rate APP между разными сессиями. Документация хранится в этом GitHub-репозитории, а не в памяти отдельного чата.

## Обязательное чтение перед работой

1. `docs/PROJECT_CONTEXT.md` — **текущее устройство и состояние** продукта, БД, API и UI.
2. `CHANGELOG.md` — **что и когда менялось**, причины изменений, ссылки на PR.
3. `docs/DECISIONS.md` — **почему** выбраны архитектурные и продуктовые правила.
4. Соответствующие файлы приложения + `docs/DEPLOYMENT.md` и, при импорте, `docs/import-audit-2026-10-15.md`.
5. При вопросах о нынешнем production дополнительно проверить GitHub `main`, CI и Vercel — текст не заменяет живую проверку.

**При расхождении:** текущий исходный код и реально проверенное состояние сервера приоритетнее описания. Устаревшую документацию исправить, а не воспроизводить ошибку. Не выдавать намерения из чата за выполненные задачи или проверки.

## Правила изменений

- Отвечать по-русски, если пользователь не просит иначе. Изменять только согласованные области; поддерживать мобильный UX, историю браузера, PWA и совместимость существующих данных.
- Работа в отдельной ветке/PR; запускать `npm run build`, `python -m unittest discover -s tests -v` на PostgreSQL, `npm run test:e2e` на мобильных браузерах согласно CI. До объявления «опубликовано» проверять целевой production на https://r-app.ru и GitHub Actions VPS deployment.
- **В рамках того же PR** обновить `CHANGELOG.md` для пользовательского изменения, `docs/PROJECT_CONTEXT.md` для изменённого факта/состояния и `docs/DECISIONS.md` при новом/пересмотренном решении. Для документационных правок одни эти файлы допустимы без нового production build.
- Записывать кратко: задача → фактическое изменение → PR/коммит → проверки → deployment → ограничения. Историю **дополнять**, не переписывать без причины.
- Не помещать сюда PIN, почту пользователей, токены API, cookie, `DATABASE_URL`, экспорт персональных данных и приватные значения переменных окружения.
- Не запускать операции с production PostgreSQL или массовый импорт без конкретного запроса пользователя, сверки целевых аккаунтов, резервной копии, идемпотентности и плана отката.
- В Rated/Completed/Dropped обязательны четыре критерия, платформа и дата; «Прохожу» **не требует** обязательных даты и платформы. Исторические оценки/даты без явного согласования не переписывать.
- В коллекции «Хочу пройти» системный slug `wishlist`, красное эмодзи ❤️ и сохранённые пользовательские членства. Не путать членство в коллекции со статусом прохождения.

## Быстрые дизайн-итерации до финального CI (26.10.2026, PR #65)

- Для серии экспериментальных правок UI открывать **draft PR** в `develop` и вносить туда небольшие итерации. На draft PR обязательные тяжёлые jobs CI (`build`, `backend-tests`, `mobile-e2e`) **пропускаются**; по необходимости запускать только локальную сборку, точечный тест затронутого компонента или визуальную проверку. Не выдавать пропущенный CI за зелёный.
- Когда вариант готов к проверке на staging, перевести PR в **Ready for review**. Это запускает полный CI для итогового HEAD; перед merge все обязательные проверки должны закончиться **success**. После merge в `develop` полный CI запускается ещё раз, за ним — автоматический staging deploy и smoke. Никаких изменений правил полной проверки production/main.
- Для PR, уже перешедшего в Ready, каждый следующий коммит снова проверяется; для очередного длительного цикла экспериментов можно вернуть PR в draft. Избегать серии CI запусков по каждому стилистическому коммиту.

## Обязательное доведение изменений до production (Definition of Done)

**По умолчанию задача не заканчивается созданием PR.** Для согласованного изменения агент обязан в рамках того же рабочего цикла:

1. Реализовать изменение в отдельной ветке, обновить относящуюся к нему документацию в том же PR, создать PR.
2. Дождаться **фактического завершения** обязательных проверок PR (build, backend, mobile E2E и другие применимые); разобрать и исправить ошибки, запустить повторную проверку. Статус «в очереди»/«в процессе» не является успехом.
3. После успешного CI **самостоятельно слить PR в `main`** без дополнительного запроса «сливать?», если пользователь не попросил оставить PR открытым и нет блокирующего требования ревью, безопасности или разрешения.
4. Дождаться CI для `main` и автоматического GitHub Actions VPS deployment; при ошибке разобраться, исправить в следующем PR и повторить до успеха. Не считать успешную сборку эквивалентом успешного деплоя.
5. Проверить реальный production `https://r-app.ru`: рабочие API и БД, публичный smoke, HTTPS, необходимый функциональный сценарий; сверить развёрнутый SHA (`/srv/rateapp/current-release`) с коммитом релиза. Для интерфейса/PWA/Push дополнительно проверить соответствующий сценарий там, где доступна нужная среда/устройство; неподтверждённое явно отметить.
6. Только после этого сообщить «готово», указав PR, коммит, результаты CI, деплоя и проверки production.

**Исключения:** пользователь явно заказал только PR/черновик, требуется отдельное разрешение на необратимую/опасную операцию, недоступны обязательные права, секреты, review или физическое устройство. В таком случае не обходить ограничения и **не объявлять задачу законченной**; конкретно указать, что сделано, что заблокировано и почему. Не обещать фоновое выполнение: все обещанные шаги делать в текущем рабочем цикле, пока доступны.

## Staging-процесс (после PR #44)

- Новые функции разрабатывать в `feature/*` от `develop`; PR в `develop` после CI доставляется и проверяется на `https://dev.r-app.ru` с изолированной тестовой БД. Приёмка на staging — отдельный обязательный этап, а не эквивалент production-релиза.
- **Не** переносить экспериментальные фичи в `main` до одобрения владельцем. После приёмки создать PR в `main`, дождаться CI, слить и проверить `r-app.ru`, VPS SHA, миграции и smoke согласно Definition of Done.
- Для инфраструктурных изменений, необходимых для запуска самого staging, разрешён PR напрямую в `main` после зелёных проверок; production безопасность и доступность должны быть проверены до bootstrap staging.
- Staging **никогда** не пишет в production PostgreSQL. Привилегированные деплойные скрипты берутся только из `main`; тестовые образы выпускаются из проверенного SHA `develop`; опасные действия с БД требуют отдельного подтверждения, резервной копии и проверки цели.
