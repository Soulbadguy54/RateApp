# Rate APP — инструкция для новых чатов и coding-агентов

**Назначение:** быстро восстанавливать проверенный контекст Rate APP между разными сессиями. Документация хранится в этом GitHub-репозитории, а не в памяти отдельного чата.

## Обязательное чтение перед работой

1. `docs/PROJECT_CONTEXT.md` — **текущее устройство и состояние** продукта, БД, API и UI.
2. `CHANGELOG.md` — **что и когда менялось**, причины изменений, ссылки на PR.
3. `docs/DECISIONS.md` — **почему** выбраны архитектурные и продуктовые правила.
4. Соответствующие файлы приложения + `docs/DEPLOYMENT.md` и, при импорте, `docs/import-audit-2026-10-15.md`.
5. При вопросах о нынешнем production дополнительно проверить GitHub `main`, CI и Vercel — текст не заменяет живую проверку.

**При расхождении:** текущий исходный код и реально проверенное состояние сервера приоритетнее описания. Устаревшую документацию исправить, а не воспроизводить ошибку. Не выдавать намерения из чата за выполненные задачи или проверки.

## Правила изменений

- Отвечать по-русски, если пользователь не просит иначе. Изменять только согласованные области; поддерживать мобильный UX, историю браузера, PWA и совместимость существующих данных.
- Работа в отдельной ветке/PR; полный `npm run build`, `python -m unittest discover -s tests -v` на PostgreSQL, `npm run test:e2e` на мобильных браузерах обязателен **для PR в `main` / перед production** или по прямому запросу владельца. Для `develop`/staging — без полного тестового прогона в цикле UI-итераций. До объявления «опубликовано» проверять целевой production на https://r-app.ru и GitHub Actions VPS deployment.
- **В рамках того же PR** обновить `CHANGELOG.md` для пользовательского изменения, `docs/PROJECT_CONTEXT.md` для изменённого факта/состояния и `docs/DECISIONS.md` при новом/пересмотренном решении. Для документационных правок одни эти файлы допустимы без нового production build.
- Записывать кратко: задача → фактическое изменение → PR/коммит → проверки → deployment → ограничения. Историю **дополнять**, не переписывать без причины.
- Не помещать сюда PIN, почту пользователей, токены API, cookie, `DATABASE_URL`, экспорт персональных данных и приватные значения переменных окружения.
- Не запускать операции с production PostgreSQL или массовый импорт без конкретного запроса пользователя, сверки целевых аккаунтов, резервной копии, идемпотентности и плана отката.
- В Rated/Completed/Dropped обязательны четыре критерия, платформа и дата; «Прохожу» **не требует** обязательных даты и платформы. Исторические оценки/даты без явного согласования не переписывать.
- В коллекции «Хочу пройти» системный slug `wishlist`, красное эмодзи ❤️ и сохранённые пользовательские членства. Не путать членство в коллекции со статусом прохождения.

## Тестовая стратегия быстрых итераций (26.10.2026, PR #65)

- **На `develop`/staging не запускать полный CI по умолчанию.** Редактировать UI короткими сериями, можно вести draft PR, но публикация preview на `dev.r-app.ru` **не требует** `backend-tests`, `mobile-e2e` и полного release build. `.github/workflows/ci.yml` на push в `develop` выполняет только минимальный маркер готовности staging, а в `vps-stage.yml` собираются frontend/API Docker-образы и проверяется здоровье staging (это техническая сборка и smoke, **не полный тестовый прогон**). Изменения могут быть сырыми, и об этом говорить явно.
- Полный комплект CI `build` + `backend-tests` + `mobile-e2e` обязателен **перед слиянием PR в `main`** и после push в `main`. По явному запросу «фича готова, давай проверим» вручную запустить `Frontend CI` через `workflow_dispatch` на нужной ветке. При сбоях фиксы перепроверять до успеха перед production.
- PR в `develop` на стадии дизайн-подбора могут оставаться draft без CI; merge/деплой на staging допустимы ради просмотра реального мобильного результата. Не переносить эти неподтверждённые эксперименты в production без приёмки и полного тестового набора.
- Не считать зелёный staging build/health доказательством качества фичи. Сохранять минимальную возможность откатить незавершённый preview при ошибках и не трогать рабочую production-БД.

## Асинхронные release-пайплайны с Telegram (правило от 27.10.2026)

**По явному согласию владельца отправить принятую версию в production агент запускает проверяемый релиз и сразу отвечает в чат ссылкой на конкретный запущенный GitHub Actions pipeline и на release PR. Не ждать окончания полного CI, main CI или VPS deployment, не опрашивать статусы циклически и не удерживать диалог ради статуса.** Указывать честно «релиз запущен / ожидает проверки», а не «готово / опубликовано».

Порядок выполнения без участия чата:

1. Изменения и документация проходят `feature/*` → `develop` → staging; для production после приёмки — PR из `develop` в `main`. Добавить метку `release-approved` **только после явного разрешения владельца** на конкретный релиз.
2. `Frontend CI` для этого PR запускает полный набор `build` + `backend-tests` + `mobile-e2e`; если хоть одна обязательная проверка не прошла, **в main ничего не сливать**, уведомить владельца через Telegram со ссылкой на ошибку. Исправления отдельным PR в `develop`, повторный запуск CI после обновления release PR.
3. Зелёные проверки разрешённого PR из `develop` в `main` автоматически запускают job `promote-approved-release`: он ещё раз сверяет живые base/head/SHA и метку перед `squash`-merge. Не обходить branch protection/review/required checks; если GitHub запрещает merge, pipeline завершится ошибкой и Telegram уведомит владельца.
4. `main` выполняет полный CI повторно. Только успех открывает `VPS production deployment` с текущими backup/migration/health/smoke; отдельный Telegram workflow присылает **финальный результат**. Никаких дополнительных ручных «ну что, сливать?» после запуска не требуется.
5. В чат при старте: конкретный PR, прямая ссылка на запущенный CI-run, какой SHA выпускается, что ещё НЕ завершено. На успех/сбой реагировать в следующем обращении владельца, не обещать отложенный ответ от этого чата. При доступности системы можно кратко проверить начальный статус, но **не дожидаться всей цепочки**.

**Исключения:** destructive/prod DB операции без согласованного backup и плана отката, неразрешённые права/review, и иные обязательные ручные ограничения. Не отключать тесты или их обязательность ради скорости. Настройка `release-approved` означает разрешение начать условный выпуск, **не** разрешение публиковать красный CI. Инфраструктурные PR в `main` вне процесса `develop` идут по отдельной ручной проверке и не автопромотируются.

## Обязательное доведение изменений до production (Definition of Done, асинхронно)

- Для завершённого *развёртывания* нужны зелёный релизный CI, успешный `main` CI, завершённый VPS deployment и проверенный production health/SHA. Они остаются объективными критериями; **ожидать их в чате больше не требуется**.
- Для завершённой *задачи запуска* достаточно настроенного, реально запущенного условного CI/CD, ссылки на него и подключённых Telegram-уведомлений. Сообщать именно «запущено», не смешивать с фактически опубликованной версией.
- При красном CI/деплое новые изменения в production не должны попасть через этот pipeline. Владелец получает ошибку в Telegram и возвращается в чат для разбора. Успешный CI должен довести релиз до production без дальнейших ручных сообщений агенту, кроме требуемых GitHub review/permissions.
- По возможности после явного согласия владельца не спрашивать дополнительное подтверждение на обычный merge и deploy; это утверждение **не** распространяется на опасные изменения данных.

## Staging-процесс (после PR #44)

- Новые функции разрабатывать в `feature/*` от `develop`; PR в `develop` может доставляться и проверяться на `https://dev.r-app.ru` **без полного тестового CI**, но с технической сборкой образов и smoke с изолированной тестовой БД. Приёмка на staging — отдельный обязательный этап, а не эквивалент production-релиза.
- **Не** переносить экспериментальные фичи в `main` до одобрения владельцем. После приёмки создать PR в `main`, добавить `release-approved`, запустить полный CI и дать ссылку на работающий релизный пайплайн; при зелёных проверках слияние/деплой делает GitHub Actions. Не ждать длительного прогона в чате; фактическое завершение подтверждается Telegram и GitHub Actions.
- Для инфраструктурных изменений, необходимых для запуска самого staging, разрешён PR напрямую в `main` после зелёных проверок; production безопасность и доступность должны быть проверены до bootstrap staging.
- Staging **никогда** не пишет в production PostgreSQL. Привилегированные деплойные скрипты берутся только из `main`; тестовые образы выпускаются из проверенного SHA `develop`; опасные действия с БД требуют отдельного подтверждения, резервной копии и проверки цели.

## Автоматическая передача после merge (hotfix от 27.10.2026)

GitHub suppresses `push` от `GITHUB_TOKEN`, которым `promote-approved-release` сливает PR. **Нельзя** ожидать, что такой squash merge сам запустит `main` CI. Job после успешного merge с проверкой SHA обязан выполнить явный `workflow_dispatch` полного `ci.yml@main` (`actions:write`); затем existing VPS production `workflow_run` ждёт зелёный main CI. Если передача не сработала — это ошибка выпуска, а не «тесты зелёные, значит готово». Проверять production по реальному SHA и health. Отличать два последовательных Telegram сообщения: одобренный release CI и независимый staging deploy (тестовая версия); только production deploy завершает публикацию.

## Второй release handoff: main CI → VPS (27.10.2026)

Из-за наблюдаемого отсутствия production workflow_run после main CI, запущенного от GITHUB_TOKEN через workflow_dispatch, больше не полагаться на каскад workflow_run для выпуска. Успешный main CI (включая production-smoke) сам делает явный workflow_dispatch vps-deploy.yml с проверенными tested_sha и ci_run_id. Deployment обязан перепроверить main HEAD, успешный исход именно этого main CI и всех четырёх обязательных jobs до GHCR publish или SSH. Если что-то не совпало — ошибочный/пропущенный выпуск, не «опубликовано»; диагностировать CI/Action, не обходить gate. Старые абзацы о workflow_run относятся к первоначальному расследованию и не являются рабочей схемой после этого исправления.
