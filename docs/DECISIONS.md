# Rate APP — журнал архитектурных и продуктовых решений

**Состояние: 19 октября 2026 года.** Это объяснение уже принятых решений, а не список обещаний. Каждому новому ADR давать номер, дату, статус и ссылку на PR/код. Ссылки ведут в этот же репозиторий.

## ADR-001 · Локальный PK + внешний уникальный ID IGDB (принято)
`games.id` — независимый внутренний первичный ключ, `games.igdb_id` — UNIQUE/index. `user_games`, жанры и алиасы связаны FK с внутренним PK. Это отделяет нашу модель отношений от внешнего провайдера и предотвращает дубликаты. См. `api/models.py` и `api/games_routes.py`.

## ADR-002 · Игра, прохождение и членство в коллекции — разные сущности (принято)
Каталог `games` общий; `user_games` содержит ровно одно пользовательское состояние игры (`user_id + game_id` unique); `collection_games` описывает независимые связи. Wishlist не должен загрязнять «Мои игры», а удаление из коллекции не стирает прохождение. PR #2, #8, #9, #11.

## ADR-003 · Серверная обязательность критериев и дат для завершённых (принято)
Для completed/dropped обязательны платформа, дата, четыре критерия в диапазоне 1–10. Агрегат считается из критериев, валидируется в API и PostgreSQL. Для playing отдельной обязательности даты/платформы **нет**, пока UI не поддерживает явный ввод даты. PR #26, #32, #33.

## ADR-004 · Шаг UI оценки 0,5, точность хранения 0,1 (принято)
Оценки выставляются в четырёх барабанах с шагом 0,5, итог округляется до 0,1 по ROUND_HALF_UP. Старые значения до 0,1 не мигрируются и сохраняются; редактирование предлагает ближайшие 0,5. PR #24, #25, #35.

## ADR-005 · Свежая Rate APP оценка важнее кэша IGDB (принято)
Средняя общественная оценка считается по completed/dropped, один голос/пользователь, кроме демо. При открытии карточки запрашивается лёгкий no-store endpoint, результат сохранения содержит пересчитанный рейтинг, а поздний ответ IGDB не должен заменить свежий агрегат. PR #1, #35.

## ADR-006 · Защищённая «Хочу пройти», но её членство независимо от статуса (принято)
Системный slug `wishlist`, наименование «Хочу пройти», красный ❤️, розовая тема. Настройки системы нельзя редактировать/удалять через пользовательский UI; добавление в неё не уничтожает существующее прохождение. PR #2, #9, #34.

## ADR-007 · Строгая UI + backend + DB-валидация, без выдуманных данных (принято)
Пустое название коллекции/невалидная цветовая схема запрещены. Поля пользовательского ввода ограничены и на UI, и в API. Не присваивать произвольные рейтинги/даты из отсутствующих источников. Импорт идемпотентен, дубликаты разрешаются по IGDB обложкам/ID. PR #23, #26, #28–#33.

## ADR-008 · Мобильная PWA с реальной browser history (принято)
Целевые клиенты — iOS/Android. Десктопный gate, загрузка с recovery, install и обновление PWA, сохранение возврата Back/Swipe после добавления игры и поиска. История браузера — источник истины; не создавать дубли экранов игры после save. PR #16–#23, #35; production blank-screen fix 16 октября.

## ADR-009 · API разнесён по доменам, миграции отдельно от cold start (принято)
FastAPI router для auth, library, collection, games/IGDB, push; общие сервисы. Миграции по Alembic выполняются отдельным контролируемым шагом. `Base.metadata.create_all` и ALTER TABLE **не на старте Vercel функции**. Последующая проверка backend CI обязательна. Аудит 16 октября, `docs/DEPLOYMENT.md`.

## ADR-010 · Секреты и аккаунты не в документации; минимальный экспорт (принято)
Argon2 PIN, HttpOnly Secure cookie, серверное хранение хэша токена, throttling. JSON export только владельца и не заменяет backup БД. Операции с данными других пользователей — лишь по явно авторизованному сценарию. `api/security.py`, `docs/DEPLOYMENT.md`.

## ADR-011 · Один контекст в GitHub и автоматическое сопровождение изменений (принято 19.10.2026)
`AGENTS.md` задаёт правила чтения, `docs/PROJECT_CONTEXT.md` описывает актуальное состояние, `CHANGELOG.md` содержит хронологию, этот файл объясняет причины. Любой PR, меняющий поведение, обновляет соответствующую документацию. GitHub `main` — единый актуализируемый источник; каждый новый чат должен реально прочитать файлы.

## ADR-012 · Docs-only коммиты не вызывают новый build (принято 19.10.2026)
Vercel `vercel.json:ignoreCommand` выполняет `scripts/ignore-docs-build.sh`. Если изменения с последнего успешного деплоя затрагивают только Markdown-документацию, скрипт возвращает 0 (skip); если есть код, изменения неизвестны или предыдущий SHA недоступен — 1 (build). Это **не** отменяет GitHub CI, Vercel audit-записи и возможного подсчёта пропущенной попытки в квоте. Проверять после настройки на docs-only коммите.

## ADR-013 · Не обозначать инфраструктурные рекомендации как реализованные (актуально)
Sentry DSN, PITR/snapshot, branch protection, production Alembic baseline — остаются операционными пунктами, пока не проверены независимо. Подробнее `docs/stability-audit-2026-10-16.md`.

## ADR-014 · Выделенный VPS, GitHub Actions и offsite pg_dump (план от 21.10.2026)

Целевое окружение: Caddy, FastAPI и PostgreSQL 18 на VPS, Docker-образы с тегом Git SHA собираются в GitHub Actions после успешного CI. Регулярный деплой по ограниченному SSH-ключу не расходует Gateway. Условие активации: отдельно проверенный первый релиз, внешние секреты и защита ветки. Перед миграциями — проверенная резервная копия, без автоматического отката схемы. Резервные копии — независимый systemd timer + pg_dump + прямой rclone Drive remote Google Drive (без отдельного шифрования, ADR-015) и проверка восстановления. Вход по SSH-паролю остаётся разрешённым по желанию владельца с дополнительной защитой. CI-аккаунт получает только ключ с принудительным SSH-командным обработчиком; отдельная root-команда проверяет, что SHA является предком актуальной main. **Статус:** production развёрнут и проверен на VPS 21.10.2026. См. [VPS_MIGRATION](VPS_MIGRATION.md).

## ADR-015 · Обычные бэкапы Google Drive без дополнительного шифрования (принято 21.10.2026, PR #39)
Владелец сознательно выбрал отказ от `rclone crypt` ради упрощения небольшого личного сервиса. Ежедневные PostgreSQL custom-format дампы сохраняются напрямую в приватный Google Drive через OAuth с разрешением `drive.file`; upload проверяется checksum, восстановление тестируется отдельно. Дамп включает email, хэши PIN, сведения о сессиях и другие данные аккаунтов, поэтому папку не публиковать. Вернуться к дополнительному шифрованию при изменении требований.

## ADR-016 · Задача завершается только после проверенного релиза (принято 21.10.2026)

По умолчанию завершением доработки Rate APP считается успешная доставка в production, а не только PR, зелёные тесты или merge. Агент должен самостоятельно завершить последовательность PR CI → merge → main CI → VPS deployment → production smoke с проверкой SHA версии, устраняя обнаруженные ошибки без повторной просьбы владельца. Исключения: явный PR-only режим, обязательное ревью/разрешение, риск необратимых действий, отсутствующие внешние доступы или проверки на реальном устройстве; в этих случаях фиксировать конкретный блокер. Подробный регламент: [AGENTS.md](../AGENTS.md) и [DEPLOYMENT.md](DEPLOYMENT.md).

## ADR-017 · Отдельный staging на общем VPS (24.10.2026, PR #44)

Решение: `dev.r-app.ru` обслуживается тем же Caddy/VPS, но отдельными frontend/API-контейнерами и отдельной PostgreSQL-базой `rateapp_stage` с **несуперпользовательской** ролью `rateapp_stage` и отдельным паролем. Тестовый API не получает production DB password, cron secret и VAPID-ключи. Production использует только `rateapp` и релизы `main`.

Тестовые данные берутся из проверенного snapshot production в момент первоначального bootstrap; оставляется `soulbadguy` с исходным Argon2 PIN-хэшем и игровой библиотекой/коллекциями, но без существующих сессий, других аккаунтов, login throttle и push-подписок. Bootstrap сохраняет оба дампа до операции и **никогда не меняет production-базу**. Повторный bootstrap автоматически не перезаписывает накопленные staging-данные.

Регистрация запрещена серверной переменной окружения, отдельно от frontend. Сайт не ограничивается IP: личные данные закрыты стандартной авторизацией; публичные статические файлы и `/api/health` не считаются приватными. Домен отмечен `TEST` и `X-Robots-Tag: noindex`. Действующие cookie не копируются; cookie остаётся host-only.

CI запускается для `develop` и `main`. `develop` после успешного CI публикует отдельные stage-образы; привилегированный SSH-dispatcher из проверенного `main` допускает только текущий commit `develop` и использует compose/scripts из `main`, не выполняет скрипты из feature-ветки как root. Новые функции тестируются на staging до принятия решения о релизе на `main`.

Предварительные условия: полный CI для PR; успешный `main` deploy/production smoke; безопасный staging bootstrap и подтверждённый `dev.r-app.ru` smoke. Контур не считать готовым до фактической проверки HTTPS и входа владельца.

## ADR-018 · Возрастной lazy-TTL и единая IGDB-очередь (24.10.2026, проект для staging)

IGDB разрешает локальное кэширование. Вместо полного периодического обновления каталога запросы осуществляются по требованию: у игр до 30 дней от релиза — 7 дней, а у игр старше 5 лет — 365 дней. При просмотре деталей устаревшие каталожные поля обновляются после ответа пользователю. Ошибка внешнего API не повреждает старый кэш. Сроки настраиваются по фактической динамике данных, без удаления старых пользовательских оценок.

Все маршруты используют один backend-коннектор с Twitch OAuth, bounded priority queue, фиксированным интервалом между запросами, ограниченными повторами 429. Известны два экземпляра FastAPI, поэтому каждому выделен ~1.33 req/s: суммарно обычная пиковая скорость меньше внешнего лимита 4 req/s. Межпроцессная гарантированная координация при увеличении количества экземпляров — отдельное последующее решение. Tinder использует этот же шлюз позднее, но его пользовательские действия и экран пока не реализованы. См. [IGDB_CACHE_POLICY](IGDB_CACHE_POLICY.md) и [DISCOVERY_PREP](DISCOVERY_PREP.md).

## ADR-019 · Discovery v1: локальный персональный feed и обратимые действия (24.10.2026; staging до приёмки)

Для первой итерации персональные рекомендации выбираются только из кешированных игр, без IGDB-запроса на свайп. Жанровые предпочтения вычисляются из пользовательских completed/dropped оценок с большим весом, чем разовые likes/dislikes, и дополняются внешним рейтингом/популярностью и детерминированным компонентом поиска нового. Одно событие на игру пользователя хранится в `discovery_feedback`; его отмена удаляет событие и только wishlist-членство, созданное этим действием. Жесты: влево like, вправо dislike, вверх wishlist, вниз подробности. `develop` → staging, до пользовательской приёмки не выпускать на `main`. В будущем проверить ранжирование на отложенных оценках и расширение общего каталога пакетными IGDB-запросами.

## ADR-020 · Discovery UI v2: full-bleed постер + pull-up sheet, переназначение жестов (24.10.2026; staging)

По уточнённому требованию владельца горизонтальные свайпы **переопределены**: влево dislike, вправо like, вверх wishlist. Это изменение UI-контракта ADR-019; серверные значения `like`/`dislike`/`wishlist` сохраняются, исторические события не переписываются. Свайпы делаются на самой обложке, без постоянных кнопок. Плавающая glass-панель раскрывается отдельным шевроном *вверх* и закрывается обратным жестом с spring/snap, а в раскрытом положении блокирует действия свайпов для защиты от случайного выбора. Рейтинги размещены справа, яркие подсказки мигают с интервалами, обучение умещается в один кадр. На staging тестируются реальные жесты Android/iOS перед выпуском на main; сервер и продовая база не меняются.

## ADR-021 · Discovery встроен в app shell, стекло и обложка независимы (24.10.2026; staging)

После пользовательской приёмки v2 выяснилось, что её полноэкранный режим, скрытая навигация, растянутый постер, крупная матовая панель и гирлянда подсказок не соответствуют UX. Решение v2 о собственном fullscreen app-shell **отменено**, bottom nav и layout приложения сохраняются. Исходное изображение не обрезается: contain и мягкий blurred backdrop. Метаданные/рейтинги лежат в маленьком полупрозрачном стекле; drag шеврона влияет только на sheet, drag постера влияет только на положительное/отрицательное/ wishlist решение и минимальный tilt, а finish анимирует один уход. Цветные направления проявляются совместно с длительными паузами; tutorial существует поверх загруженной первой игры. Сохраняем направления из ADR-020: право like, лево dislike, вверх wishlist. Поставляется и проверяется только на `develop`/staging до разрешения main.

## ADR-022 · Discovery cover edge-to-edge, стекло — overlay 80% (24.10.2026; staging)

Слова «всё пространство между верхней и нижней панелями» считаются **точной геометрической спецификацией**, а не желательным приближением. В предыдущем UI полноразмерность была потеряна из-за общих отступов `.page` и двойного вычитания высоты в `.discover-screen`. Теперь `.page--discovery` снимает собственные поля и нижний зазор, оставляя в неприкосновенности навигационные панели. Stage/poster совпадают по геометрии со свободной областью viewport; оригинальный постер не искажается и не обрезается (`contain` + фон из той же обложки). Небольшое liquid glass с шевроном и метаданными располагается поверх постера и по отдельному жесту расширяется до 80% его высоты. Поскольку постер независим от шеврона, его размеры и положение при раскрытии не изменяются. Реальная мобильная геометрия проверяется E2E с допуском 2px. Эксперимент только на develop/staging до пользовательской приёмки.

## ADR-023 · Discovery: непрерывный постер под прозрачным liquid glass (24.10.2026; staging)

При визуальной проверке v4 выяснилось, что `contain` оставляет снизу только тёмный ambient backdrop, отчего метаданные выглядят вторым независимым блоком, хотя их DOM расположен поверх постера. Для основного экрана рекомендаций приоритетнее **непрерывность изображения за стеклом**: использовать `object-fit:cover` с сохранением пропорций и контролируемым crop по краям, убрать дублированный ambient-слой, ослабить tint и `backdrop-filter` стекла. Высота нижней полосы определяется реальным размером текстово-рейтинговой группы через ResizeObserver, а не заранее назначенным пиксельным диапазоном; верхние углы постера закругляются. Критерии проверяются мобильным E2E. Прежние решения ADR-021/022 о `contain` заменяются именно в UI Discovery. Staging до приёмки владельца, production без изменений.

## ADR-024 · IGDB Game snapshot хранить целиком, Discovery без сетевого запроса при раскрытии (24.10.2026; staging)

Новый контракт: при внешнем поиске сохранять весь **возвращённый** `games` JSON в nullable `igdb_payload JSONB`, а не выбрасывать поля, которые текущий UI ещё не использует. Query включает `fields *` плюс понятные expansions для пользовательских деталей; связанные endpoint-объекты за пределами ответа API не загружаются без отдельного задания. Структурированные поля `games` и `details_json` используются как быстрый проекционный кэш для поиска/отображения. Раскрытие Discovery — синхронное действие над данными первоначального feed, а `/api/games/{id}/details` читает исключительно локальный PostgreSQL. Для исторических `igdb_payload IS NULL` — ограниченный ручной backfill; никаких массовых IGDB запросов из UI. Соблюдать суммарный глобальный IGDB лимит и поочерёдные внешние запросы staging/production.

UI выбор: приоритет сохранения целого названия/надписей на постере над crop: `contain` для HD переднего постера + размытое, светлое background fill в том же холсте. Это пересматривает ADR-023 `cover` лишь для визуального слоя, не возвращая отдельную нижнюю плашку. Подсказка у верхнего края, up-gesture получает небольшой preview tilt/scale/y, стекло реагирует на swipe из любой точки кроме внешних ссылок (tap переключает только шеврон).

## ADR-025 · Discovery: сверху полная обложка, обучение только размытием и текстом (24.10.2026; staging)

После приёмки v6 выбрано `object-fit:contain; object-position:center top` вместо вертикального центрирования: при неполной высоте постера ambient blur остаётся преимущественно **снизу**, под стеклом, а изображение не обрезается. Изменение касается только Discovery, не миниатюр каталога.

Обучающий экран должен сохранять первую игру под размытием и исключить собственную визуальную карточку, декоративные рамки и отдельную CTA-кнопку. Оставить только центральное описание назначения рекомендаций и три направленные текстовые подсказки с последствиями жестов; закрывать любое касание overlay. Невидимая доступная кнопка на всю площадь сохраняет keyboard/screen reader доступ без визуального UI; повторный вызов через `i`. Предыдущие детализированные style-решения заменяются этим в Discovery, остальные жесты и стекло неизменны. До приёмки `main` не обновлять.

## ADR-026 · Discovery: натуральный постер вместо заполнения всей высоты (24.10.2026; staging, заменяет часть ADR-023/024/025)

Размер изображения **не должен повторять размер всей области Discovery**. Вписать картинку целиком с сохранением пропорций, ограничить реальными границами viewport, прижать к верхней панели и скруглить все четыре угла. Не создавать декоративную размытую копию, заполняющую оставшуюся высоту. Пустота между нижним краем короткой обложки и стеклом — допустима и окрашена `var(--bg)`, в том числе во время смены игр. Стеклянная панель — независимый нижний слой, не дочерний элемент трансформируемой обложки; может перекрывать длинный постер при открытии. Старые указания о continuous blurred image background отменены только для Discovery. Проверять на разных соотношениях сторон, без влияния на мобильную навигацию и другие типы карточек. Production не обновлять до пользовательской приёмки staging.

## ADR-027 · Привязка свёрнутой панели к высоте постера, тёмное стекло и мягкий blur обучения (24.10.2026; staging)

Владелец отменил произвольный зазор между обложкой и нижним стеклом из ADR-026. Оставляем 12px между верхней навигацией и постером, но верхнюю грань свёрнутого стекла рассчитываем по **фактической** нижней границе видимого изображения. Для высоких картинок приоритет у минимально читаемого блока названия/оценок: он может перекрыть низ постера. Для широких стекло достраивает пространство до нижней навигации. При смене игр непрерывный (не keyed) слой стекла пружинит между положениями; раскрытие по прежнему показывает не меньше 80% рабочей области. Тонировка тёмно-синяя для белого текста, не непрозрачная заливка. Обучающий overlay анимирует реальный CSS backdrop-filter от 0 до 7px вместо мгновенного 17px. Проверять Chromium/WebKit и обложки 3:2 / 2:1. Только staging до принятия.

## ADR-028 · Независимая прокрутка описания, бережная локализация и обратная связь свайпа (25.10.2026; staging)

Отказаться от перехвата прокрутки всего glass: вертикальные touch/scroll внутри нижнего описания **не закрывают** раскрытую панель. Фиксированные метаданные, платформы и компактные внешние иконки располагаются до описания; скролл доступен только самому тексту. Верхний/нижний отступ относительно обложки одинаков — по 12px, без искажения пропорций. При конфликте высоты обложки и видимой панели уменьшать изображение, а не скрывать блок действий. Подложка загрузки равна цвету интерфейса, стекло меньше тонировано.

Поскольку IGDB отдаёт summary/storyline преимущественно на английском, а UI русскоязычен, локализовать **только открываемое описание**, без отправки данных аккаунта внешнему переводу. Для публичного текста используется MyMemory в пределах документированных сегментов (не гарантируется SLA/квота). Отдавать настоящий машинный перевод на русском или явно обозначенный исходный английский fallback; никогда не выдавать автоматический перевод за гарантированный. Запрашивать на demand, кешировать успех. Свайпы получают ранний небольшой наклон (только горизонтально — как перелистывание) и краткий directional glow, не отдельный confirm step. Повторять тесты iOS/Android; production ждёт одобрения владельца.

## ADR-029 · Discovery: направленный flick и долговечная пара EN/RU (25.10.2026, staging, PR #56)

## ADR-030 · Discovery: edge fog, непрерывный pan и преддекодирование обложек (25.10.2026, staging, PR #57)

Вместо рамки и свечения по border — рассеянная дымка на физических краях рабочей области с вырезанной глобальной нижней навигацией. ## ADR-031 · Семантическая палитра и последовательное появление обучения (25.10.2026, staging, PR #60)

Для часто встречающихся взаимодействий оставить нейтральную основу плюс три уже существующие цветовые семьи: зелёная `like` (emerald коллекций), холодная синяя `dislike` (blue), розовая wishlist (`rose`). ## ADR-032 · Жестовый слот навигации без ухудшения обычного tap (25.10.2026, эксперимент на staging)

Объединять не всю панель сразу, а только «База игр» и «Для тебя» в одном из четырёх привычных мест. Долгое удержание раскрывает Motion spring/bounce bubble с выбором непрерывным движением пальца и отпусканием; свайп по самой кнопке меняет постоянно видимый ярлык, но **не** меняет экран. Приоритет — обычному tap: 390 мс на удержание, 46 px горизонтального смещения на свайп при небольшом вертикальном дрейфе, без автоматической навигации от случайного touch движения. Предпочтение хранить локально по пользователю, не отправлять на сервер и не вмешиваться в browser history при простом перелистывании ярлыка. Раздел `discovery` продолжает использовать обычный URL/Back.

Использовать существующий Motion (без дополнительной зависимости), `pointer capture` + coordinate hit-test для сквозного drag к всплывшему меню и reduced-motion fallback. Поддерживать клавиатурный выбор. До приёмки реального touch на `dev.r-app.ru` решение имеет статус **staging experiment**; `main` не меняем.


## ADR-033 · Нативное расширение панели + мгновенная цель после свайпа (25.10.2026, staging)

Для жестового подпункта использовать именно материал и структуру `bottom-nav`, а не акцентный отдельный tooltip: та же непрозрачность, blur и тонкая граница, без стрелки снизу; кнопки имеют такую же иконку/подпись. Spring/bounce анимирует раскрытие из выбранного слота, локальная фиолетовая active-surface показывает принадлежность к IGDB; остальной Rate APP остаётся зелёным. Цвет IGDB не дублировать в компонентах: один токен в `:root`, повторно используемый рейтингом Discovery.

Не привязывать подавление после свайпа к таймеру: только созданное жестом событие click должно игнорироваться. Начало нового pointer sequence сбрасывает suppression. Закреплённый tab обновляется в синхронном ref прежде React state/анимации, иначе быстрый swipe→tap может попасть в старый маршрут. Никаких изменений серверной модели или истории при простом перелистывании.


### Дополнение к ADR-033 — положение и жидкая анимация (26.10.2026, PR #64, staging)

Всплывающий блок в устойчивом состоянии должен полностью находиться **над верхней границей** `bottom-nav`, а не над верхом её внутренней кнопки, смещённой на padding. Оставлять видимый зазор и никакого постоянного хвостика. Попап-навигация использует ровно тот же размер SVG (22px), подпись (8px) и геометрию/цвет активной подложки (фиолетовый токен IGDB), что нижняя кнопка. На открытии временно допустима только анимированная «жидкая перемычка», исчезающая до завершения раскрытия. Вместо fade/blur из пустоты выбран непрозрачный морфинг формы капли через Motion spring и интерполяцию скруглений, с выключением при reduced-motion. Сохранять жесты и маршрутизацию ADR-032.


## ADR-034 · Абсолютный размер popup и CI только по завершении итераций (26.10.2026, PR #65, staging)

**Решение по UI:** пункт подплавающего меню должен иметь совпадающие с реальной нижней кнопкой не только SVG 22px и подпись 8px, но **весь прямоугольник (ширину + высоту)**. Для мобильной адаптивности измерять обычную кнопку через ResizeObserver; отдельные фиксированные размеры кнопок popup запрещены. Визуально жидкое появление — непосредственный `motion.path` morph от капли через вытянутую форму к панели, а не обычный scale/blur контейнера; контент проявляется после расширения, без постоянного выступа в конечном состоянии. Учитывать `prefers-reduced-motion`.

**Решение по тестам (уточнение владельца 26.10):** полный CI не запускается автоматически ни при PR в `develop`, ни при push в `develop`. Это контур дизайн-итераций; можно сливать даже draft после снятия draft-флага ради preview на staging. На staging обязательны лишь сборка Docker frontend/API и smoke; это не означает прохождения E2E/backend-тестов. Полный CI проводить **перед merge PR в `main`** и после push `main` либо по явной команде владельца (ручной `workflow_dispatch` на `develop`). Стадия Ready у PR в develop не запускает полный CI сама по себе. Возможные промежуточные UI-ошибки допустимы только на staging и должны быть устранены к production-приёмке. Для `main` послаблений нет.

## ADR-035 · Четвёртый жест Discovery и единая анимация навигационного пузыря (26.10.2026, staging, PR #67)

Свайп вниз по обложке — переход к существующему вводу прохождения этой игры. Без автоматической оценки, создания статуса и записи `discovery_feedback`: только навигация с корректным Back. Палитра жестов остаётся ограниченной уже существующими темами: для нового действия — янтарная тема коллекции, токен `--palette-playthrough-rgb` и `docs/COLOR_PALETTE.md`; новые случайные тона не вводить. Дополнительное направление должно сопровождаться ярлыком/обучением и световым откликом. Для стабильного мобильного pan сглаживать Motion springs, не перезапускать reset и exit одновременно.

Морфинг нижнего пузыря должен иметь **один временной источник** для поверхности, контура и интерактивного содержимого; независимые деревья presence и delayed spring/layout на закрытии создавали рассинхронные кадры. Пока только staging, полное QA перед main или по запросу владельца.

## ADR-036 · Discovery без верхнего Back и двухшаговый Android exit (26.10.2026; staging, PR #68)

Discovery — корневая вкладка общего shell, а не вложенная страница каталога. Верхние «Вернуться в базу игр» и «Шаг назад» не показывать; ручная смена вкладок возможна только через общий bottom nav. Направленная надпись свайпа принадлежит экрану, не постеру: фиксированное положение 50%/50%, чёткий текст без glow/blur; мягкий туман допустим только у краёв рабочего пространства.

При системном Back из корневого состояния не допускать случайного выхода: первая попытка показывает предупреждение, повторная в течение трёх секунд разрешает выйти. Реализовать это через собственный same-origin History API sentinel/gate, не блокируя browser Back и свайпы на вложенных страницах (добавление прохождения, детали игры). На повторе попробовать `window.close()` только для standalone и выйти за пределы SPA-истории через `history.go`; гарантию закрытия native Android приложения веб-API не дают, проверить вручную. Не подменять реальный выход переходом в «Базу игр». Не дублировать gate при reload.

## ADR-038 · Финальные уведомления о CI/CD в Telegram без постоянного polling (27.10.2026; PR #74)

Решение: результаты проверок и деплоя должны доходить до владельца автономно через GitHub Actions, а не через повторяющиеся запросы статуса в чат. Разделять fast staging preview (только образ и smoke), релизный полный CI (backend/build/mobile-e2e), staging deploy и production deploy. Ожидаемые сообщения — **один итог на значимый этап**: успешный staging-deploy, успешный production-deploy, успешный/неуспешный ручной релизный CI или PR CI, а также неудача без последующего этапа. Исключить дубли промежуточных успехов, отменённые проверки и ежедневный успешный health. Не называть быстрый `develop` прогон полным QA.

Доверенный `workflow_run`-слушатель размещать исключительно в default `main` и выполнять только проверенный код main, а не payload, скрипты/артефакты feature-веток. Отправлять сообщения через Telegram Bot API и `parse_mode=HTML` (яркие эмоджи, статусы, links) с экранированием текста из event. Токен хранить только в GitHub Secret `TG_BOT_TOKEN`, личный идентификатор адресата — только в Actions Variable `TG_CHAT_ID`. Если переменные не заданы, workflow должен явно завершаться ошибкой, а не притворяться успешной доставкой. Отдельный `workflow_dispatch` проверяет доступность Telegram без деплоя. Критерий активации — реально успешный тестовый workflow и полученное уведомление.

При добавлении интеграции запрещается автоматически переносить ещё не принятые staging-функции на production. PR: https://github.com/Soulbadguy54/RateApp/pull/74

## ADR-039 · Релиз по ссылке: не ждать CI в ChatGPT, автослияние строго после зелёных тестов (27.10.2026; release PR #70)

Владелец меняет определение интерактивного цикла: после **явного разрешения** выпуска агент запускает релиз и возвращает ссылку на конкретный GitHub Actions run, не удерживая сессию до окончания полного тестирования/деплоя. Авторитетный результат проверки — GitHub, уведомление владельцу — Telegram; ошибки разбираются по его следующему сообщению. Объективная Definition of Done у опубликованного приложения не меняется: build + backend + mobile E2E + main CI + успешный VPS deployment/smoke.

Для `develop`→`main` PR с `release-approved` применяем автоматизированный GitHub Actions `promote-approved-release` в `ci.yml`, с `needs: [build, backend-tests, mobile-e2e]`. Перед слиянием повторно проверять live PR base/head, origin repo, точный tested SHA и label. Делать squash-merge только через GitHub API с expected SHA, который соблюдает branch protection/review. По красным проверкам или ошибке merge ничего не продвигать в production; telegram sender отправляет ошибку и ссылку. Новые staging-итерации не получают release label автоматически; привилегированные секреты не доступны незнакомым fork PR. Это заменяет требование ADR-016/034 вручную дожидаться полного прогона при запуске релиза, **не** заменяет обязательность полного CI перед публикацией.


## ADR-040 · Тесты защищают контракты, а не изменчивые декоративные токены (27.10.2026, аудит develop)

При разработке предпочтительно **сокращать лишнее и переиспользовать тест**, а не прибавлять число сценариев к каждому исправлению. После переезда на VPS шесть тестов Vercel `ignoreCommand` признаны неактуальными и удалены; 84 оставшихся backend-теста удерживаются, потому что охватывают независимые инварианты и выполняются за считанные секунды. Для Discovery E2E не следует проверять десятки косметических CSS-свойств с точными RGBA/тенями, достаточно проверки функциональной структуры, геометрии постера и поведения реальных жестов; визуальные подробности принимает владелец на staging. Не маскировать зависания повышением общего тестового таймаута: локализовать ожидание отсутствующего элемента.

Ожидание в чате только для коротких ≤2 мин проверок; сложные пайплайны >5 мин стартуют с передачей ссылки, конечный статус сообщает Telegram. Для интервала 2–5 минут оценивать ожидаемое время. Полный тестовый CI до production/явной просьбы не запускать, а production gate обязательно сохранять. Подробный перечень: `docs/TEST_AUDIT_2026-10-27.md`.

## Дополнение к ADR-038 · Различать цель PR и исходную ветку в Telegram (27.10.2026, PR #76)

Нельзя считать каждый `head_branch=develop` свидетельством staging: обязательные pre-production проверки запускаются на PR `develop → main`, а источником остаётся `develop`. Из GitHub event брать `pull_requests[].base.ref` и номер PR, отображать в уведомлении оба направления и явную метку «Production · релизные тесты» либо «Staging · PR-проверки». Для успеха релизных тестов писать, что production ещё не обновлён; для ошибки — что выпуск заблокирован. Если PR metadata недоступны, не угадывать цель по `head_branch`. Не путать CI с отдельными staging/production деплоями.


## Дополнение к ADR-038 · Деплойное Telegram-сообщение как SHA-привязанный мини-CHANGELOG (27.10.2026)

Не называть любой успешный deployment выпуском всех ожидающих задач. Сообщать точно `production` или `staging`, краткий SHA реально развёрнутых контейнеров и до четырёх проверяемых изменений **от предыдущего успешно опубликованного SHA**. Список формируется из GitHub compare и сообщения squash-коммита/содержания объединённого PR, а не из всех непубликованных разработок. Для staging обязательно брать SHA из артефакта `publish` job: `workflow_run.head_sha` относится к доверенному main workflow и может быть неверен для develop source. Если точное основание сравнения отсутствует, не выдавать сочинённый полный changelog; GitHub API-задержка или недоступность не должны отменять уведомление о деплое. Не расширять тестовый набор ради формата: изменять существующие unit-кейсы.

## ADR-040 · Сохранять блокировку card pan с момента старта до окончания (27.10.2026, release QA #70)

Начавшийся при открытой или движущейся glass-панели жест обложки недействителен на всём интервале pointer stream: даже если `expanded` поменялся до `onPanEnd`, не записывать реакцию и не открывать форму прохождения. Блокировку сохранять в `posterPanBlockedRef`, сбрасывать на `onPanEnd`, не вводить задержек для новых самостоятельных свайпов.

## Дополнение к ADR-040 · E2E проверяет факт завершения анимации и истинную hit target (27.10.2026, release QA)

Нельзя начинать новый cover swipe, пока закрытие стекла находится в transition: `aria-expanded=false` и `glass.y > stage.y+90px` не означают `reveal≈0`. Инварианты Motion pan, смены знака без прыжка и отсутствие случайной реакции сохраняются. Таймауты не увеличивать без нужды; от проверки не отказываться.

## ADR-041 · GITHUB_TOKEN merge не вызывает main push: обязательный явный CI dispatch (27.10.2026)

В full-release PR #70 три набора тестов прошли, `promote-approved-release` успешно сделал squash merge в main, но из-за GitHub `GITHUB_TOKEN` suppression push-workflow **не возник новый main CI** и VPS оставался на старом SHA. Решение: после успешного trusted merge, сравнения возвращённого SHA с текущим main HEAD и проверки `release-approved`, агентский CI делает явный `workflow_dispatch` полного `ci.yml` на `main`; GitHub разрешает такие вызовы `GITHUB_TOKEN` (`actions:write`). Основной набор тестов и production-smoke не обходить, VPS production-trigger по-прежнему принимает только успешный `Frontend CI` `main`.

Одноразовая инфраструктурная реанимация `fix/release-handoff-ci-20261027` допускается в ограниченный approved-release gate с проверками identical SHA/label/same repo; это не разрешение merge другим feature-веткам. Сообщения Telegram о зелёном PR CI означают успешные проверки/слияние, **не** физический продакшен. Если `workflow_run.pull_requests` пуст после merge, успех ограниченного `promote-approved-release` является безопасным признаком main-bound release; staging-деплой обязан прямо говорить, что r-app.ru не менялся.

## ADR-042 · Прямой защищённый dispatch production после main CI (27.10.2026)

Фактически проверено: после PR #83 успешный workflow_dispatch Frontend CI run #40441005013 на main=2d6c8200 не создал downstream VPS production deployment через workflow_run, хотя все 4 проверки завершились успешно; production оставался на dab74554. Нельзя объявлять выпуск опубликованным только по main CI.

Решение: избавиться от недетерминированной зависимости VPS production deployment от косвенного события workflow_run. Теперь main CI с needs: build, backend-tests, mobile-e2e, production-smoke запускает явный workflow_dispatch с точным tested SHA и CI run ID. Доверенный VPS workflow перепроверяет живую ветку main, SHA и conclusion=success исходного Frontend CI, а также 4 успешных обязательных jobs до выдачи образов/SSH. Внешний trigger без валидного проверенного main CI не публикует ничего. Сохранить возможность остановить ошибочный релиз, уведомления о реальном VPS-деплое, текущие backup/migrations/rollback. Старый workflow_run отключён для предотвращения двойного запуска.

## ADR-043 · Завершённая публикация и единый перехват защищённого 401 (27.10.2026)

Факт: production VPS выпустил d9add1d67dee (Actions run #40444398986), но после этого успешного запуска событие Telegram workflow_run не возникло. Решение: доставку Telegram success/failure встроить последним независимым notify-production job в VPS production workflow; не полагаться на цепочку GITHUB_TOKEN → workflow_dispatch → workflow_run. Сообщение «Production обновлён» разрешено только после зелёного deploy и независимого публичного /api/health с environment=production и доступной БД. Отказ Telegram виден как отдельная неуспешная job, даже если приложение опубликовано. Старый production workflow_run слушатель отключён для исключения дубликатов.

В исходном UI поисковая ошибка английского «Session expired» и ошибка рекомендаций происходят при одном и том же защищённом 401, когда старый cookie не соответствует PostgreSQL AuthSession. Не связывать это с истечением токена IGDB. Реакция клиента на 401 после авторизации: локально сбросить только состояние аутентификации/кэши экрана, показать форму логина с понятным русским пояснением; не повторять мутации, не чистить БД и не делать logout при временных 5xx. Bootstrap до входа и собственные auth-запросы обрабатывают свои 401 самостоятельно.

### Дополнение к ADR-043 — 401 должен быть durable событием (27.10.2026)

В CI PR #85 оба WebKit 401 E2E падали, пока Android проходил. Голое `window.dispatchEvent` для истёкшей сессии теряет одноразовое событие, если защищённый fetch завершается до подписки `useEffect` в App. Выбран boolean external-store с `useSyncExternalStore` и стабильным snapshot: ответ 401 сначала запоминается, затем приложение может прочесть его в следующем render независимо от порядка child/parent effects. При успешном новом логине флаг сбрасывается; при 503 никакого logout. Подтверждать тестами на WebKit, а не повышением timeout.

## ADR-044 · Однозначные имена upstream в общем Docker network (27.10.2026)

Критический наблюдаемый факт: `rateapp-api-1` (production) и `rateapp-stage-api` (staging) на shared `rateapp_internal` оба анонсируют Compose alias `api`. Использовавшийся в production Caddy `reverse_proxy api:8000` не гарантирует, в какой контейнер попадёт запрос; после зелёного deploy #40458962549 публичный /api/health фактически отвечал `staging`, поэтому Telegram job вернул failure **после успешной отправки сообщения**. Это потенциальная подмена окружения/данных, не недостаток проверки. Выбор: production proxy всегда направлять на уникальный `rateapp-api-1:8000` (гарантируемый `name: rateapp` в Compose), а staging — `rateapp-stage-api:8000`; не использовать общие короткие alias `api` или `web` на shared сети. Реализованы немедленный Caddy reload на VPS и постоянный repo fix + regression tests. Не смягчать post-deploy environment==production. Отдельно валидировать production и staging после каждого deploy.

## ADR-045 · Локальная история вкладки и выход только из корня (27.10.2026, staging)

После использования общего нижнего меню пользователь начинает новый навигационный путь. Browser Back/edge swipe возвращает по экранным шагам текущего пути, включая осмысленные cross-link переходы из карточки игры в конкретную коллекцию. Он не раскрывает прежнюю вкладку после достижения корня новой.

Реализация через History API в src/App.tsx: выбор нижней вкладки заменяет старую локацию новым корнем, любой новый корневой экран получает same-URL sentinel exitGate через pushState с прежним 1,8-секундным двойным Back. Повторный выбор активной вкладки из вложенного экрана заменяет его корнем и восстанавливает sentinel; сбрасывает ранее показанный exit toast. Внутренние страницы, формы и cross-link сохраняют обычный браузерный Back и восстановление UI-снимков. Сам выход PWA не гарантирован browser API (ADR-036/037). E2E проверяет внутренние и глобальные шаги. До приёмки только develop/staging; перед main нужен полный release QA.

## ADR-046 · Сброс только библиотечных фильтров при возвращении в PWA (27.10.2026)

Пользователь ожидает, что новый вход в приложение начинает просмотр «Мои игры» без фильтров предыдущего захода. Простого начального `useState([] / 'all')` недостаточно: Android/iOS PWA при переходе в фон часто оставляют тот же документ и React-состояние активными. Выбрано локальное lifecycle-правило: только после перехода `document.visibilityState` hidden→visible либо `pageshow.persisted` сбрасывать статусы, жанр, платформу и закрывать панель фильтров. Повторная авторизация в том же UI также очищает фильтры. Обычные переходы по нижней навигации/Back фильтры сохраняют. Сортировка и поиск не являются фильтрами и сохраняются; записи/БД/API/навигационная история не изменяются. Не добавлять скрытый тайм-аут или sessionStorage persistence; повторный запуск в новом документе уже получает начальные значения. Мобильный E2E симулирует hidden→visible и bfcache и проверяет отсутствие сброса при внутриприложенных переходах.

## ADR-047 · Сохранённые ссылки, очередь и отложенное сопоставление игр (29.10.2026, develop/staging)

Для внешних материалов вводятся только две дешёвые PostgreSQL-таблицы: пользовательские ссылки и извлечённые названия с **необязательной** FK на существующую игру. Ни пользовательские прохождения, ни рейтинги, ни wishlist не затрагиваются до отдельного явного действия. Единственный устойчивый игровой ID — уже известный `games.id` (в публичном JSON — `games.igdb_id`); новый провайдерский ID и принудительный импорт игры не нужны. Получение кандидатов ChatGPT не является доказательством существования карточки IGDB.

Фоновая обработка осуществляется одноразовыми командами Gateway внутри выбранного API-контейнера с проверкой `VERCEL_ENV`, без дополнительных публичных webhooks или секретов в промпте. `SELECT … FOR UPDATE SKIP LOCKED`, lease на 2 часа, токен одной выдачи, идемпотентный повтор и три попытки защищают от конфликтов по часовому расписанию. Никакой постоянный worker, браузер, LLM или HTML не живёт в API RAM; пакет ограничен тремя ссылками/80 именами, сохранение пользователем ограничено по числу/скорости. Новая схема добавляется отдельной Alembic-миграцией, staging и production физически разделены; production требует отдельного одобренного релиза. До подключения реальных ссылок требуется отдельный проверенный SSRF-safe extractor и договорённость о работе с видео/соцсетями. См. [SAVED_LINKS](SAVED_LINKS.md).

## ADR-048 · Поиск связанных игр по тем же правилам, что «База игр» (29.10.2026, develop/staging)

После `submit` названия попадают в `saved_link_games` как строки. Отдельный bounded `resolve` берёт до 4 названий за один запуск, сначала выбирает **первого** кандидата из существующего локального поиска (названия, альтернативные имена, `pg_trgm`, приоритет полного совпадения и популярности), затем при пустой выдаче применяет **тот же** IGDB поиск и page ranking, включая альтернативные имена. Рейтинг в поисковом ранжировании означает популярность по количеству оценок/hype, а не средний пользовательский балл Rate APP; менять эти веса специально для импорта нельзя. Сохраняется только победившая IGDB-карточка и ссылка `SavedLinkGame.game_id`; исходное имя не перезаписывается и ни одно прохождение/коллекция не пополняется автоматически.

Серверный проход отделён от дорогого получения статей и ChatGPT Tasks, имеет 15-минутный lease (не интервал расписания), три попытки при временных ошибках и терминальный `no_match` при честном отсутствии. Запросы к IGDB имеют низкий фоновый приоритет, по 4 имени максимум за тик; при увеличении количества процессов необходим единый межпроцессный limiter для общего лимита IGDB. Staging- и production-контуры используют разные Docker-контейнеры и БД, разные Gateway/ChatGPT задачи. Никаких одновременных подключений экспериментальной задачи к production, никаких секретов в промптах. Окружение обязательно проверяет `--expect-environment`. См. [SAVED_LINKS](SAVED_LINKS.md).

На Gateway Free минимальный интервал расписаний — 60 минут. Часовое staging-расписание сопоставления `gsc_01M61ZA6VQ00CJF3Z4JJZBSRGX` создано в состоянии pending: для активации требуется подтверждение владельца в https://trygateway.sh/schedules. ChatGPT Scheduled Task для настоящих URL по-прежнему **не создана**; старый эксперимент с тестовым файлом не является реальной очередью.

## ADR-049 · Постоянны только ссылки и массив ID, очередь и GPT-названия временны (29.10.2026, develop/staging)

**Заменяет модель ADR-047/048 в части хранения и единицы работы**, сохраняет локальный-first + IGDB-first-ranked алгоритм. В конечном состоянии `saved_links` хранит владельца, URL, статус и `game_ids INTEGER[]` с локальными первичными ключами из `games`. Пары «сырой GPT title → game_id» не нужны; каталогические метаданные, обложки и рейтинги при открытии реестра берутся из общей `games` одним SQL-запросом для страницы. PostgreSQL массив не поддерживает FK на каждый элемент, поэтому все новые ID валидируются перед сохранением, а удаление игры автоматически выполняет `array_remove` через AFTER DELETE trigger на `games`. GIN индекс ускоряет затронутые строки.

`saved_link_jobs` — **одна временная запись на одну ссылку**, содержит список извлечённых GPT-названий, lease, прогресс/курсор и промежуточные найденные ID. Сохранение ссылки создаёт эту запись, удаление ссылки немедленно каскадно удаляет задание; поздние ответы со старым ID/токеном не могут его возродить. `claim --limit 1` получает один URL, `resolve --limit 1` ищет **все его игры**, но ради ограниченных ресурсов не дольше 120 секунд или 12 названий за проход, затем продолжает то же задание при следующем запуске. На окончании все валидные ID одним атомарным commit переходят в `saved_links.game_ids`, а временное задание со всеми GPT-названиями удаляется. Если статью не удалось обработать за три попытки — очередь очищается, сама ссылка остаётся как failed. Рейтинг совпадений остаётся общим с каталогом. Исторические таблицы и связи перенести в Alembic `20261029_06`, не менять пользовательские оценки/прохождения. Сначала staging, production только с явным одобрением и полным CI.

## ADR-050 · Одна таблица: пользовательская ссылка, имена GPT и связанные ID (29.10.2026, develop/staging)

**Пересматривает ADR-049.** У пользователя есть единственная уникальная строка `saved_links` на URL: `id`, `user_id`, `url`/`url_hash`, `created_at`, `game_names TEXT[] NULL`, `game_ids INTEGER[]`. Сырые GPT-имена, даже если не удалось разрешить игру, остаются в этой пользовательской строке до удаления ссылки или явного обновления. Никакой таблицы `saved_link_jobs` или долговременной пары «имя – ID» больше нет. Заполненный массив имён не является кешем веб-страницы для других пользователей: он снимок результата обработки конкретной сохранённой ссылки.

`NULL` для `game_names` значит ещё не проверено, пустой массив значит проверено и не найдено игр. Для ChatGPT выбираем **старейшую** строку `WHERE status='pending' AND game_names IS NULL ORDER BY created_at,id LIMIT 1`, с временной арендой в самой строке, чтобы два запуска не брали одну работу. `submit` записывает имена туда; `resolve` последовательно пополняет `game_ids` через тот же local-first/IGDB-ranked поиск. Обработка одного источника может продолжаться между часовыми запусками из-за лимита 12 имён/120с; курсор тоже хранится в той же строке. Удаление мгновенно исключает работу; повторный ответ с устаревшим токеном игнорируется. Изменение содержимого статьи не отслеживается автоматически: пользовательский `POST /refresh` сбрасывает старый снимок и ставит ссылку в начало новой обработки.

Постоянные `game_ids` — локальные PK. Реестр запрашивает по ним игры из `games` без сетевых вызовов; существующий PostgreSQL delete-trigger удаляет ID отсутствующих игр. Alembic `20261029_07` переносит незавершённые старые задания в ту же строку и удаляет их таблицу, не затрагивая главную `games`. Для ранее завершённых ссылок названия восстановить невозможно, поэтому сохраняем уже известные ID и предлагаем refresh. Production только после явного согласия и полного CI.

## ADR-051 · Совместимость колонки GPT имён после однотабличного импорта (29.10.2026, develop/staging)

## ADR-052 · Web Risk + pinned HTTP reader + strict ChatGPT task; Gateway permissions unchanged (29.10.2026, staging)

Сохраняем собственную лёгкую таблицу `saved_links` и существующий `claim/submit/resolve` контракт, добавляем строго обязательную `prepare` команду между claim и submit. GPT **не получает raw URL в claim**. Только команда prepare с действующим ID/lease принимает URL из PostgreSQL, синхронно вызывает Google Web Risk Lookup на каждый URL/redirect и только при успешной чистой репутации загружает HTML/text. Отсутствие `WEB_RISK_API_KEY` или ошибка сервиса означает **fail closed** без отправки содержимого. API сам не скачивает URL. Web Risk требует API key и включённого billing, Lookup до 100000 запросов/месяц бесплатно по тарифам Google, URL пересылается Google (учесть приватность внешних ссылок).

SSRF-политика для HTTP reader: `canonical_url` и запрет credentials/нестандартных портов; `getaddrinfo` проверяет **все** IP; соединение идёт на выбранный проверенный публичный IP без повторной резолюции, но с исходным TLS SNI/hostname/certificate/Host. Не используем внешние proxy, cookies, сессии и JS; каждый redirect проверяем заново через Web Risk, блокируем private IP и HTTPS→HTTP; ограничения 1MB ответа, 15с общего бюджета, 3 redirects и 60000 символов текста. HTML очищается по тегам/служебным блокам; это не полноценная гарантия удаления prompt injection или рекламы.

Строгий ChatGPT-план в `docs/GPT_SAVED_LINKS_TASK.md` требует использовать только claim→prepare→submit, воспринимать чужие страницы как данные и не выполнять команды из них. По явному решению владельца **техническая изоляция Gateway на этом шаге отложена**; нельзя считать промпт полноценной sandbox или отсутствием риска использования SSH. Не подключать production и не активировать GPT-задачу до проверки в staging. Игры и их ID остаются в одной строке, браузер/медиакодеки и новые модели на VPS не устанавливаются.

## ADR-053 · Safe Browsing v5 instead of Web Risk for noncommercial URL screening (29.10.2026, staging)

**Supersedes ADR-052 in provider/key/billing only.** On owner request, external saved-link reputation checks switch from paid-billing Google Web Risk to free **Google Safe Browsing v5** (`urls:search`). Allowed only while Rate APP usage stays **noncommercial**; re-evaluate license/provider before any monetization. API key must be restricted to Safe Browsing API in Google Cloud. Server accepts `SAFE_BROWSING_API_KEY` or an existing staging `WEB_RISK_API_KEY` alias (temporary compatibility), but talks exclusively to Safe Browsing and does not fall back to Web Risk. Malicious URL match blocks the download, API failure and malformed results fail closed. Check every redirect; keep pinned HTTPS/SSRF protection and the user-controlled source snapshot contract. Raw URLs are shared with Google. Existing no-Sandbox/Gateway risk disclaimer from ADR-052 remains.

### ADR-053 implementation clarification — protobuf wire format (29.10.2026)

Safe Browsing v5 `urls:search` returns `application/x-protobuf` on successful requests; assuming JSON blocked every URL despite an HTTP 200. Use a bounded local parser for the exact documented `SearchUrlsResponse` fields `threats=1` and `cache_duration=2`, with strict MIME and malformed-message rejection, rather than adding Google SDK/runtime deps to the small VPS container. Every URL and redirect must still be checked independently; neither a missing duration nor a corrupted threat payload is considered safe. Verified with a benign URL and Google's sample malware URL on the staging host (not fetched as pages). This only repairs the provider's wire format and preserves the earlier noncommercial licensing, fail-closed and production constraints.

## ADR-056 · «База игр» — эталон UI, проверяемое превью и Back сначала отменяет выбор (31.10.2026, develop)

**Вместо независимых размеров каждого экрана** считать `renderAdd` («База игр») единственным визуальным эталоном H1, полей, управляющих кнопок, внешней сетки и вертикальной плотности; `UI_DESIGN_GUIDE.md` содержит явную инструкцию для следующих PR. Tap по карточке открывает источник в новой вкладке, отдельная кнопка «Открыть» не нужна, мусорка красная/контурная.

Отдельный просмотр превью через `POST /api/saved-links/{id}/preview` выполняет Google Safe Browsing + pinned DNS/TLS + редиректы + размер/time/MIME ограничения того же защищённого считывателя, что GPT, и только после этого извлекает `title/og:title/description`. При браузерном `popstate` transient UI (selected collections, selected collection-games, selected links, confirm dialogs, overlays, pending delete countdown) поглощает первый Back. Восстанавливается текущее состояние history/exit gate без всплывающего «выйти» и без перехода к другой вкладке; только следующий Back обрабатывает обычную историю. Это правило распространяется на gesture-back Android/iOS и на аппаратную кнопку.

## ADR-057 · Идемпотентный long-press, круговой delete progress и строго ограниченные Instagram картинки (31.10.2026)

В режиме мультитач нельзя считать `pointerleave` надёжным признаком окончания удержания: при 480мс pointer capture сохраняет событие на исходной карточке; `pointermove > 10px`, `pointercancel` и `pointerup` прерывают ожидание. Нативный `contextmenu` после hold не должен менять selection ещё раз. Повторный click не может открывать внешнюю ссылку. Для 4-секундного отложенного удаления используется один непрерывно заполняемый полупрозрачный `conic-gradient` слой поверх фона корзины, иконка поверх слоя; он синхронен с моментом отправки DELETE, вместо сегментных штрихов/чисел.

Для Instagram видео HTML часто сообщает профиль вместо content-specific названия. Парсить caption из media-specific `on Instagram: ...`, иначе нейтральная «Видео Instagram». Instagram oEmbed более не предоставляет `thumbnail_url`; обходы через произвольные URL/iframe и прямые CDN загрузки на клиенте запрещены. Пользовательская картинка по возможности проксируется собственным authenticated API только после безопасной проверки HTML и конкретного OG-image от Instagram CDN с HTTPS, SSRF/DNS/TLS, Safe Browsing, MIME/магической сигнатурой и лимитом 512KB. На ошибке, avatar-only/логин-странице — локальный placeholder, без ложного изображения и без раскрытия адреса пользователя внешним img-тегом. Это частичная поддержка публичных Reels, не обещание обхода Instagram access controls.

## ADR-058 · Превью сохранённых ссылок без привязки к провайдеру (31.10.2026, принято для develop)

**Отменяет Instagram-специфичные части ADR-057.** Вместо отдельных обработчиков для Reels, YouTube, статей и иных сайтов один строгий парсер стандартных семантических метаданных: Open Graph, Twitter Card, JSON-LD (разбираемый как данные без исполнения JS). ## ADR-059 · Экономный text-first подход для Scheduled Task сохранённых ссылок (31.10.2026, develop)

**Решение:** стандартная scheduled GPT-задача не анализирует видеоряд: никаких кадров, OCR, скриншотов/мультимодального распознавания и скачивания/декодирования видео или аудио. Сначала дешёвый HTML/article/caption/meta-text, затем при реальной необходимости **готовый текст субтитров/VTT/SRT/transcript**. Subtitle fetch разрешается только в отдельно реализованном, ограниченном и Safe Browsing/SSRF-guarded **серверном prepare-reader**; сам агент по-прежнему ограничен теми же тремя существующими Gateway-командами и только `prepare.content`. В текущей версии reader subtitles **отсутствуют**. Следовательно, этот PR фиксирует промпт, но **не обещает работающий загрузчик субтитров**. Для источника с одним boilerplate и недоступным видео — `error:"unavailable"`, а не `games:[]`; настоящий пустой результат допустим только после содержательного текстового чтения. Анализ кадров, если решим делать, проектировать как отдельную premium-функцию с отдельной стоимостью, безопасностью и согласием. Никакого Scheduler/prod включения этим PR.

## ADR-060 · Автокарусель найденных игр, строгий resolver и бюджет свободного text-only GPT (31.10.2026, develop)

**Обновляет ADR-059 в части субтитров:** задача GPT сама решает, какой дешёвый текстовый метод выбрать: main article/caption/meta, если не хватило — публичный web search/open текста, в том числе опубликованной расшифровки/субтитров, если возможность доступна. Не строить специальный subtitle downloader на стороне backend ради этой задачи; встроенный защищённый `prepare` остаётся обязательным security gate. Дополнительный web — **только по проверенному названию/контексту**, с верификацией совпадения источника, не по внешним инструкциям. Не перезаписывать оценки или сами игры.

**UI:** если `games.length > 0`, карточка URL расширяется анимированным блоком с горизонтальной cover-каруселью «Игры из ссылки», иначе остаётся компактной. ## ADR-061 · Кеш интерфейса, IGDB идентификаторы и похожие игры (31.10.2026, develop)

## ADR-062 · Направляющие стрелки на каруселях, стабильные загрузчики и touch hold (31.10.2026, develop)

**Общее правило UI:** все горизонтальные игровые карусели должны показывать маленькие зелёные стрелки на тех краях, куда есть доступная прокрутка. Discovery h1 слева, info справа.


## ADR-062 · Нативная инерция прежде собственной физики и честная Push-диагностика (31.10.2026, develop)

Принято: горизонтальные игровые карусели общего CarouselArrows должны вести себя как обычные touch-поверхности мобильной платформы: естественный fling, на поддерживающих OS/browser — мягкая elastic граница, без принудительного скриптового перехвата touch и без случайных открытий игр при drag. Десктопная мышь/стилус получают управляемый velocity-based fling с decay и ограниченным до 15px визуальным bounce; для reduced-motion дополнительных анимаций нет. Создавать новые карусели через общий компонент и использовать эти правила, но не распространять bounce на вертикальный документ, delete/selection жесты и accessibility keyboard.

У текстовых превью новых URL таймер эффекта не должен преждевременно отменять проверенный fetch по причине списка, заменённого после POST; кэш не должен маркировать неполученный metadata как успешно загруженный. Разводим browser.permission и серверный push_ready: только при поддерживаемом Web Push, активном сервере и permission=default выводим кликабельный призыв с Notification.requestPermission под user gesture. denied требует ручных браузерных настроек, server disabled честно означает проблему конфигурации (не запускать ложный permission prompt). Красная контурная SVG иконка без emoji. В BottomNav liquid-обводка использует один цветной stroke на всех фазах без серого слоя/двойного rim, закрытие inline picker клипуется во внешней оболочке и не анимирует padding/border.


## ADR-063 · Усиленная touch-инерция, обратимое сердце wishlist и единый in-app loader (31.10.2026, develop)

**Общий загрузочный паттерн:** единый `ContentLoading` для внутренних страниц: одно вращающееся кольцо в цвете текущего раздела (фиолетовый IGDB, зелёный Rate APP), понятная одна фраза непосредственно под ним; никаких упоминаний API/серверов/названий источников при обычном ожидании. `prefers-reduced-motion` отключает rotation. ## ADR-066 · Sticky glass должен быть частью scrollport, а поиск — частью header (01.11.2026)

Уточнение/коррекция ADR-065: отрицательный margin-top у sticky header **не является** корректным способом компенсировать page padding на scrollport — при закреплении top:0 исходная область padding может остаться без blur и показать неразмытую полосу выше шапки. Решение: в обычных .page--viewport убрать padding-top, сохранить --page-top-inset только внутри header padding. Header касается y=0 viewport на первом кадре и после scroll; учитывать safe-area внутри прозрачной поверхности. Горизонтальные margin остаются отрицательными для компенсации gutter. Discovery и window-scroll Library имеют собственный геометрический путь.

Продолжаем один стеклянный материал для всех краевых панелей, включая fixed bottom-nav: var(--header-glass-background), var(--header-glass-filter), квадратные края и тонкий контур только на контактной кромке (верх bottom-nav, низ header). Desktop нижняя панель не возвращается к отдельной непрозрачной капсуле. Поиск в «Базе игр» и раскрываемая URL-форма в «Моих ссылках» — дочерние элементы соответствующего sticky header; их нельзя размещать прокручиваемыми соседями и нельзя создавать второе непрозрачное стекло на самих полях. Текстовые поля имеют общий размер 52px, border-radius14, font14 и кнопку подтверждения32px; Enter и стрелка эквивалентны. В каталоге Enter подтверждает автопоиск закрытием клавиатуры, а в URL форме отправляет POST.

YouTube DNS failure не даёт основания отключать Safe Browsing/public-IP pinning. После повторного Safe Browsing для официального валидного 11-char YouTube video URL допустим честный generic label и запрос известной обложки с i.ytimg.com через все обычные проверки. ## ADR-067 · Hover-only popup, тактильное раскрытие и подтверждение ссылок (01.11.2026, develop)

## ADR-067 · Hover-only popup, тактильное раскрытие и подтверждение ссылок (01.11.2026, develop)
