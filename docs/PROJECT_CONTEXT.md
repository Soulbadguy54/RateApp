## 1. Что мы строим

Rate APP — mobile-first веб-приложение/PWA для поиска игр, персональной библиотеки и дневника прохождений, оценки по четырём критериям, своих коллекций и списка «Хочу пройти». Мобильные Android и iOS — целевые устройства; на десктопе показывается специальная заглушка с блюром. Браузерная навигация (включая Android Back и iOS swipe), экран загрузки, приглашение установить PWA и механизм обновлений — часть продукта.

**Адреса (актуально на 21.10.2026):** production https://r-app.ru ; GitHub https://github.com/Soulbadguy54/RateApp ; старый Vercel project `rate_app` поставлен на паузу. Код и документация — в одном репозитории. UI русскоязычный.

## 2. Технологии и карта кода

- Фронтенд: React 19, TypeScript, Vite, Motion, PWA через vite-plugin-pwa. Главный роутинг/состояние экрана `src/App.tsx`, отделённые модули `src/components/`, `src/views/ProfileView.tsx`, `src/collectionModel.ts`, `src/data.ts`, CSS (`src/styles.css` и выделенные файлы), установка/запуск/PWA.
- Бэкенд: Python FastAPI `api/index.py`; разнесённые маршруты `api/auth_routes.py`, `api/library_routes.py`, `api/collection_routes.py`, `api/games_routes.py`, `api/push_routes.py`. Переиспользуемые сервисы `api/library_service.py`, `api/collections_service.py`, `api/security.py`, модели `api/models.py`, PostgreSQL engine `api/database.py`.
- БД: PostgreSQL на Neon + SQLAlchemy. Версионные миграции через Alembic (`migrations/`), **не** во время serverless cold start. Описание операций: [DEPLOYMENT](DEPLOYMENT.md).
- Каталог: IGDB + Twitch OAuth только **сервер-сервер**; IGDB обложки с `images.igdb.com`. Игра из IGDB кэшируется локально. Поиск сперва по локальному каталогу, при отсутствии/по запросу — по IGDB.
- Уведомления: Web Push с подписками устройств и VPS systemd timer для `/api/cron/release-alerts` (исторически Vercel Cron), ежедневная проверка даты релиза игр из системной коллекции. Отдельная настройка VAPID обязательна; код наличия функции не доказывает настройку внешнего сервиса. Первое приглашение `PushOnboarding` из `src/PushSettings.tsx` отображается после `/api/push/config` и готовности Service Worker; после нажатия `PushManager.subscribe()` обращается к браузерному/системному Push-провайдеру, а `PUT /api/push/subscription` уже к FastAPI. В PR #42 от 21.10.2026 эти этапы выделены в интерфейсе, а ожидания worker/провайдера/API ограничены 8/20/10 секундами; проверить на реальном устройстве после публикации.
- Опциональный мониторинг Sentry frontend/backend; наличие пакета ≠ заданные DSN/алерты.

## 3. Данные, индексы и внешние ключи

- `games.id` — локальный PK; `games.igdb_id` — внешний **UNIQUE с индексом**, уникальные ID IGDB предотвращают дубликаты каталоговых игр.
- `users.id` — PK пользователя. `user_games` связывает пользователя и игру по FK; уникальность `(user_id, game_id)`: не более одной библиотечной записи на игру на пользователя. Даты, платформа, статус, 4 оценки и отзыв принадлежат этой записи.
- `collections`: пользователь, уникальный slug, название, цветовая схема, эмодзи. `collection_games` — join-таблица FK на коллекцию и `user_games` с уникальным `(collection_id, user_game_id)` и датой добавления; членство в коллекции **не равно** прохождению.
- Есть FK с каскадным удалением, таблицы жанров/алиасов, сессий, push-подписок/доставок; `pg_trgm` индексы по названиям и альтернативным названиям для неточного поиска. Подробнее — SQLAlchemy `api/models.py`, `api/games_routes.py`.
- Метаданные об играх и details/store/trailers сохраняются в БД; обогащённые данные IGDB кэшируются (актуальный TTL деталей смотреть в `api/games_routes.py`). IGDB результат не должен заменять свежий вычисленный рейтинг Rate APP.

## 4. Прохождения и оценки — важные инварианты

- Статусы `completed` (Пройдено), `dropped` (Дропнуто), `playing` (Прохожу). `wishlist` и `untracked` — технические placeholder-состояния для коллекций, **не** самостоятельные прохождения в «Мои игры».
- Для **Пройдено/Дропнуто** требуются: выбранная платформа, дата окончания/дропа и **все 4 критерия** (`atmosphere`, `story`, `technology`, `gameplay`), каждый от 1 до 10. Проверки в Pydantic API и PostgreSQL CHECK (условная обязательность, старые строки по необходимости `NOT VALID`).
- Для **Прохожу** дата начала и платформа *не обязательны* на бэкенде; текущая форма позволяет выбрать платформу, но **не имеет отдельного барабана/поля выбора даты начала**. Не вводить NOT NULL для playing без согласованного UX.
- Барабаны (PR #35) дают **шаг 0,5** (1,0; 1,5; …; 10,0). Существующие оценки с точностью до 0,1 в БД сохраняются; при открытии редактора барабан округляется к 0,5. Средний итог из 4 критериев — до десятых по `ROUND_HALF_UP` (и DB CHECK).
- Общая оценка Rate APP — среднее **по одному итоговому баллу на пользователя** среди completed/dropped, без демо-пользователя. Количество голосов — число оценивших. Во время редактирования другими людьми значение меняется; страница запрашивает свежий `GET /api/games/{game_id}/community-rating` c `Cache-Control: no-store` и предотвращает позднюю перезапись старым ответом IGDB.
- После добавления прохождения из «Базы игр» браузерная история возвращает через «Назад» в сохранённый поиск; **не создавать второй идентичный экран игры** (регрессия PR #35).
- **Навигация по вкладкам (27.10.2026, develop):** нажатие пункта общего нижнего меню начинает независимую цепочку Back от корня выбранной вкладки — прежнюю вкладку системным Back не открыть. Повторный выбор выбранной вкладки сбрасывает дочерний экран. Внутренние переходы (включая переход из игры в конкретную коллекцию/форму) остаются в browser history и поддерживают Android Back/iOS edge swipe с восстановлением поиска/scroll. На корне всех вкладок первый Back показывает exit toast, повторный за 1,8 с запрашивает выход; браузерное API не гарантирует закрытия PWA. Это frontend staging до приёмки и полного release QA.

## 5. Коллекции

- Системная коллекция `wishlist` с названием **«Хочу пройти»**, эмодзи **❤️** (PR #34), розовой схемой и запретом на удаление/изменение служебных свойств. Игра может состоять в wishlist и одновременно иметь настоящее прохождение. На обложках игр отдельная «метка желания» не нужна.
- Пользовательские коллекции: название (не пустое, максимум 32 символа), описание (до 500), допустимая цветовая схема, качественные эмодзи через Twitter artwork из emoji-picker-react; интерактивное редактирование, удаление, управление членствами и массовые действия. Градиенты **намеренно приглушены** по запросу.
- Удаление из коллекции не должно удалять настоящее прохождение и оценки. Для untracked без других членств возможна очистка placeholder-записи.
- Переходы, кнопки «+», возвращение со страницы редактирования и контекстные действия должны сохранять ожидаемую историю/scroll.

## 5а. Сохранённые ссылки (29.10.2026, develop/staging)

- Текущая схема после уточнения требований: **одна** таблица `saved_links`, уникальность `(user_id,url_hash)`, PK `id`, дата `created_at`, URL, `gpt_names TEXT[] NULL` и `game_ids INTEGER[]` внутренних `games.id`. Названия от GPT сохраняются **в этой строке**, пока пользователь не удалит её; отдельной временной или постоянной таблицы очереди/пар названий нет. `NULL` означает не проверено, `[]` — проверено без игр; состояние и lease для безопасных повторов также в строке.
- `saved_links_worker claim --limit 1` читает самую старую `status=pending AND gpt_names IS NULL` (с возобновлением expired lease), `submit` пишет имена прямо туда, `resolve --limit 1` из каталога/IGDB заполняет `game_ids` в том же месте. До 12 имён/120с за проход, один URL с продолжением курсора. В реестре все карточки игр подгружаются одним SQL-запросом к общей `games` по массивам ID.
- Удаление ссылки удаляет оба массива и отменяет работу; `POST /api/saved-links/{id}/refresh` позволяет заново проанализировать изменившийся источник, сбрасывая прежний снимок. Глобального кеша результатов ссылок и обмена результатами между пользователями **нет**. Триггер PostgreSQL на удаление игры из каталога по-прежнему удаляет битый ID из массивов.
- Alembic `20261029_07` переносит текущие in-flight данные из `saved_link_jobs`, затем удаляет таблицу. Старые уже завершённые строки сохранили только game ID и не могут восстановить старые GPT-названия — повторный refresh исправляет это. Production по-прежнему без этой фичи. UI и запланированная реальная ChatGPT задача ещё впереди. Документ: [SAVED_LINKS](SAVED_LINKS.md).

## 6. Поиск, карточка, профиль, вход

- «База игр»: поиск по названию, локальные результаты и при необходимости IGDB, пагинация. Карточка игры: IGDB сведения, год/жанр/разработчик, диапазон часов, ссылки магазинов и трейлера, оценки IGDB и Rate APP отдельными блоками, свои критерии/отзыв.
- **Детальная карточка, develop/staging (29.10.2026, уточнение после PR #93):** IGDB/RateApp панели — по одной горизонтальной строке с подписью слева и крупной числовой оценкой справа (шкалы /100 и /10 неизменны, компактная адаптация до 360px). При отсутствии рейтинга вместо «—»/делителя справа показано двухстрочное центрированное серое «Нет / рейтинга», той же типографикой, что прежний делитель. Кнопка выбора коллекций циклически меняет центральный контурный SVG значок `layers` на **монохромный `Icon name="heart"`** того же набора, что нижняя навигация; размеры и центровка обоих — **19×19 px**. При этом слои остаются нейтральными, а контур сердца использует существующий розовый акцент wishlist `rgb(var(--palette-wishlist-rgb))` (`#ffa2ca`), без нового цвета. Полный цикл 7,2 с, две мягкие смены по 2,52 с с ease-in-out и паузами; при `prefers-reduced-motion` оставлены неподвижные слои. Это **визуальная подсказка**, не другая кнопка и не команда wishlist; защищённая системная коллекция продолжает иметь своё красное ❤️. Открытие выбора коллекций, членство и серверные оценки не меняются.
- «Мои игры»: только реальные прохождения, фильтры по статусу/жанру/платформе, сортировки. Системный wishlist в отдельной коллекции.
- Профиль: информация аккаунта и push-настройки, раздел **«Резервное копирование»** (JSON экспорт только своего аккаунта), недоступные пока действия по изменению email/PIN обозначены явно, версия приложения **в самом низу** (PR #35).
- Регистрация: nickname 3–16 латинских символов/цифр/_, новая регистрация PIN 6–8 цифр; старый PIN из 4 цифр всё ещё допустим при входе. Auth: argon2 PIN hash, HttpOnly Secure SameSite cookie, хэш токена в БД, ограничение попыток входа. **HTTP 401** — отсутствие/истечение сессии; **5xx/сеть** — экран повторной загрузки, а не принудительный logout.
- PWA: install приглашение, `/install`, splash/loading с прогрессом; защита от blank screen при старых JavaScript assets; пользователь подтверждает обновление, без внезапного перезапуска во время формы.

## Discovery v4 · edge-to-edge карточка между системными панелями (24.10.2026; staging)

После очередной пользовательской проверки обнаружена основная причина «картинки в картинке»: даже внутри обычного `app-shell--viewport` у класса `.page--viewport` оставались общие 18px бокового padding, верхний отступ, bottom-gap и ограничение ширины; сама `DiscoverView` дополнительно вычитала эти пространства из собственной высоты и скругляла область постера. Жидкое стекло находится **над** постером (`position:absolute; bottom:0`), содержит все метаданные/рейтинги и движется по отдельному gesture на handle. Развёрнутая высота — 80% реальной высоты `.discover-stage`; исходный peek по-прежнему только 125–149px. Порог/сопротивление и направления действий не меняются. ## Discovery v5 · один непрерывный постер и glass с высотой по содержимому (24.10.2026, staging PR)

Корректировка поведения v4 по осмотру на телефоне: `object-fit:contain` визуально отделял нижнюю панель, поскольку исходное изображение заканчивалось выше glass и под ним оставался только тёмный ambient blur. Теперь один `Cover` с `object-fit:cover; object-position:center top` проходит на всю высоту `.discover-stage`, включая участок под стеклом; тёмная дублирующая ambient-картинка удалена. При ином соотношении сторон могут быть обрезаны боковые части постера, но само изображение не деформируется. Отмечено как осознанный компромисс в пользу целостного холста.

Liquid glass остаётся `position:absolute; bottom:0; z-index:3` поверх того же `Cover`, но визуальный градиент имеет alpha около 0.035–0.055, backdrop blur снижен до 10px, отражения/тени ослаблены — постер различим под стеклом. Размер `peekHeight` равен **33px handle + измеренная через ResizeObserver высота `.discover-sheet__summary-row` + 8px** (с ограничением от высоты полного sheet), а не фиксированным 125–149px диапазоном. Таким образом, и короткий, и длинный заголовок занимают ровно необходимую площадь. `.discover-stage` получил `border-radius:22px 22px 0 0` с overflow clip. Верхняя и нижняя навигация, способы свайпов, предел развёртывания 80%, API и DB остаются прежними.

## Discovery v6 + полнота локального каталога IGDB (24.10.2026, staging)

**Схема:** к `games` добавлено nullable `igdb_payload JSONB` (Alembic `20261024_03`). API `/api/games/search?source=igdb` запрашивает `fields *` вместе с вложенными описательными полями (cover, alternative_names, genres, platforms, involved_companies, websites, videos, artworks, screenshots, themes, keywords, game_modes, player_perspectives). Всё возвращённое сохраняется в `igdb_payload`, дополняя существующие ключи на частичном refresh; нормализованные индексированные столбцы остаются для быстрого поиска. UI-ready `details_json` обновляется **во время кэширования** (summary, storyline, store links, trailer; старые storyHours/completionHours сохраняются). Не обещать, что один `fields *` автоматически раскрывает бесконечные связанные IGDB endpoint-графы: в JSONB хранится полный `Games` response со значениями вложенных expanded links, а оставшиеся reference IDs можно расширять отдельными bounded заданиями.

**Отображение:** `_game_payload` передаёт summary/storyline, ссылки и время прохождения из локальных таблиц. `GET /api/discover/feed` уже содержит детали рекомендованных карточек; открытие шеврона в `DiscoverView` не делает fetch. `GET /api/games/{id}/details` **строго PostgreSQL-only**; старые записи без summary выдают пустое описание до заполнения кэша, а не блокируют UI ожиданием IGDB. Предусмотрена идемпотентная ручная партия `python -m api.igdb_backfill --limit 100 --batch 8` (по популярности, только `igdb_payload IS NULL`); не выполняется при импорте модулей, не запускается автоматически, должна адресовать только нужную БД и соблюдать глобальные квоты IGDB.

**Изображения/жесты:** в полноэкранной Discovery карточке IGDB `t_cover_big_2x` заменяется на более высокий `t_1080p` только для текущей карточки (миниатюры каталога неизменны). Передний `object-fit:contain; object-position:center center` сохраняет всю обложку, под ним размытая копия того же HD-изображения закрывает фон *в том же холсте*; glass поверх. Подсказка up в 10px от верхней границы. При pan вверх до действия карточка слегка поднимается и уменьшается, после порога `wishlist` проигрывается exit вверх; горизонтальные действия без изменений. За glass можно тянуть из handle, названия, рейтингов и описания; клики по ссылкам не перехватываются. Обычный tap вне шеврона не открывает и не закрывает панель.

При переходе Discovery вниз в форму прохождения теперь обязательно сбрасывать Motion-смещения карточки, чтобы возврат браузера/переход между view не удерживали незавершённый пан-жест. Для экрана Discovery системный Back остаётся guarded root exit, не навигацией к предыдущей вкладке; старые E2E из периода до ADR-036 актуализированы под этот UX. Визуальная проверка не должна фиксировать один frame промежуточной spring-анимации как устойчивую ошибку: координаты должны вернуться в допуск 2px после settle. Полный CI для релизного PR #70 выявил 5 падений мобильных E2E при успешных сборке и backend. Исправления проходят повторный полный CI до merge main. Документация включена в тот же PR.

### Релизный CI — тестирование анимаций после навигации (26.10.2026, PR #72)

В мобильных Playwright-сценариях после swipe-down→форма→Back нельзя использовать transient координату moving spring как стабильную базу: сначала ждать естественного положения обложки на stage (12px), затем сравнивать отсутствие её движения при свайпе glass в допуске 2px. Для liquid-nav во время выхода прежний SVG остаётся в DOM до завершения morph, поэтому факт наличия SVG не означает нового успешного long press; для подтверждения надо ждать aria-expanded=true на самой кнопке. Эти E2E поправки обнаружены полноценным release QA PR #70, не отменяют ни один сценарий и повторяются на Chromium/WebKit до main.

### E2E мобильной геометрии Discovery — invariant stage-relative (26.10.2026, PR #73)

После полного Chromium/WebKit CI остаётся один flaky тест обложки на Android, связанный с абсолютной экранной координатой при смещении mobile viewport. Для независимости обложки от движения glass правильный инвариант: poster bounding y минус discover-stage bounding y == 12px с допуском <2px; абсолютная координата body не является частью контракта. Один крупный end-to-end сценарий Discovery получает timeout 75s вместо 35s для медленных runner, сами проверки не выкинуты. PR #70 продолжает быть gate перед production и должен полностью пройти после этого изменения.

## Асинхронный условный релиз (27.10.2026, ADR-039)

Новый контракт работы агента: **после приёмки на staging, явного разрешения выпуска и создания/обновления `develop` → `main` PR** агент метит его `release-approved`, запускает полный `Frontend CI` и сразу присылает владельцу ссылку на фактически запущенный Actions run, не опрашивая его до окончания. Все исходы приходят в уже настроенный Telegram через `Telegram CI/CD notifications`; это не фоновая работа ChatGPT.

`ci.yml` для `pull_request` в `main` запускает сборку, backend/PostgreSQL и мобильные Playwright E2E. Только если три job зелёные, `promote-approved-release` проверяет, что PR из того же репозитория, head по-прежнему `develop`, base `main`, метка утверждения сохранена и HEAD SHA не поменялся. После этого делает squash merge через GitHub API c защитой SHA. При красных тестах **никакой публикации**, Telegram сообщает о сбое. После merge отдельный full CI `main` автоматически запускает существующий защищённый VPS production deployment; только успешный deploy сообщает о завершённой публикации. PR #70 — текущий конкретный релиз, впервые использующий контракт; до завершения его CI не называть выпущенным.

Без разрешающей метки обычный main PR не сливается автоматически. Отдельное ручное ревью и защита веток сохраняют силу; workflow не имеет права обходить их. При необходимости владелец открывает GitHub Actions ссылку из начального ответа и Telegram-уведомления. Установка/проверка Telegram Secret `TG_BOT_TOKEN` и repository variable `TG_CHAT_ID` завершена ранее, доставка в Telegram подтверждена workflow run #40380025330.

## 11. Telegram-сводки CI/CD (27.10.2026, PR #74)

Workflow `.github/workflows/telegram-notify.yml` на основной ветке получает только завершённые события `workflow_run` от `Frontend CI`, `VPS staging deployment`, `VPS production deployment`, `RateApp daily production health`. Приложение не делает Telegram-запросов. Доверенный скрипт `scripts/telegram_ci_notify.py` формирует аккуратную HTML-карточку с результатом, ссылкой на Actions, длительностью и (для полного CI) поимённым статусом build/backend/mobile-e2e/smoke. CI staging `develop` по ADR-034 — preview без полных тестов, и **не** маркируется сообщением «полный CI прошёл». Для `main` об успехе сообщает уже завершённый production deploy, а не промежуточный успешный CI; неудача CI сообщается сразу. Про отмену/skip и ежедневный успех health не уведомлять.

Конфигурация: GitHub repository secret `TG_BOT_TOKEN` (не пересылать в чате), repository Actions variable `TG_CHAT_ID` (числовой Telegram chat ID; не коммитить адресата в публичный исходный код). Новый бот должен быть запущен адресатом через `/start`. После задания обеих переменных инициировать `Telegram CI/CD notifications` → `Run workflow` с main: это независимая безопасная проверка реальной доставки. До подтверждения этого запуска и сообщения в Telegram **не считать интеграцию активированной**.

`workflow_run` исполняется только из дефолтной ветки `main`; checkout всегда делает `ref: main`, не исполняет код feature/PR, запросы Telegram скрывают токен от логов. Ошибка Telegram-уведомления не меняет уже завершённый результат тестов или деплоя, но отмечается красным отдельным workflow. После staging-приёмки релиза сохраняются прежние правила тестирования и промоушена.

## Telegram: отличие production release CI от staging (27.10.2026, PR #76)

## Мини-CHANGELOG в Telegram deployment-событиях (27.10.2026)

Скрипт `scripts/telegram_ci_notify.py` после успешного *реального деплоя* добавляет 12-символьный `SHA` и до 4 пунктов, полученных через GitHub REST `compare/<previous>...<current>` для **двух реально успешных запусков одного deployment workflow**. Старые production-запуски без артефакта могут сверяться по `head_sha`, staging без подтверждённого SHA не приписывает себе изменения. Если GitHub API недоступен, сообщение отправляется с честной пометкой о недоступности состава; CI/test/deployment результат не изменяется. Тесты сообщения переиспользуют прежние кейсы.

### Граница жеста Discovery/glass (27.10.2026, release PR #70)

`posterPanBlockedRef` запоминает недопустимое начало swipe при `expanded`, `reveal>0.03` или активном вытягивании glass. Если панель закрылась до `onPanEnd`, он по-прежнему игнорируется: один и тот же жест не может одновременно сворачивать подробности и запускать реакцию карточки/переход в прохождение. Для устойчивого E2E используется прямой событийный поток строки метаданных, в отличие от некорректного screen-point hit testing во время transform. Android drag за handle проверяется реальными pointer-событиями отдельно.

### E2E: дождаться полного завершения glass-collapse перед новым swipe (27.10.2026, release PR #70)

Последний Android E2E в длинном сценарии Discovery получал нулевой `translateX` после возврата из раскрытой панели: тест проверял лишь `sheet.y-stage.y > 90`, что допускает продолжающийся `reveal > 0.03`. Защита `posterPanBlockedRef` по ADR-040 правильно блокировала начатый до закрытия pan. Корректная синхронизация: сравнивать текущий верх glass с `Math.min(posterBottom+12, stageHeight-minPeek)` с допуском 2px в координатах stage. Для нового реального pointer-event выбирать точку на открытой области `.discover-cover__gesture` строго над glass, проверяя `document.elementFromPoint`, а не центр full-stage overlay (который может находиться под стеклом). Функциональная проверка непрерывного left→right→center жеста остаётся.

### Исправление пропущенного main CI после автоматического merge (27.10.2026)

PR #70 автоматически слит после успешного полного release CI #40438886429 в commit `8b4f326ca0f2aae84117ffc05fa7da95ebba2575`; VPS release marker до исправления остался `dab7455468d071ef4b3100c6407d8ab4f769fe9c`. GitHub подавляет `push`-событие, если merge выполняется CI-`GITHUB_TOKEN`! Поэтому state `main` и физический production разошлись без ошибки зелёного PR workflow. Нельзя объявлять выпуск по одному PR или staging-сообщению.

Новое восстановление: после SHA-checked merge `promote-approved-release` вызывает GitHub REST `actions/workflows/ci.yml/dispatches` (`ref=main`) с `actions:write` — это разрешённое GitHub исключение из токенного suppression. Затем штатный `workflow_run` VPS production deployment срабатывает **только** на успешный main CI. Точечная recovery-ветка `fix/release-handoff-ci-20261027` имеет ограниченный gate через ту же `release-approved` метку/точный SHA для доставки самого исправления; рабочие feature-ветки не получают автоматических прав. Для проверки: main CI, VPS production deployment, текущий `/srv/rateapp/current-release`, `/api/health` и актуальный SHA `main`. Telegram отдельно называет релизный CI, main CI и staging без ложного «production уже обновлён».

### Production/staging Docker DNS upstream collision — 27.10.2026 (после #85)
