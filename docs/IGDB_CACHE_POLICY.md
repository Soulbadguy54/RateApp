# IGDB: кэш, лимиты, приоритеты (staging, октябрь 2026)

## Что действительно меняется
- **Часто меняется:** дата/статус релиза у предстоящих проектов, IGDB rating / число голосов сразу после релиза, некоторые обложки/названия.
- **Редко меняется:** платформы, жанры, разработчик, магазины и трейлеры у старых игр. Но URL магазинов могут стать нерабочими, поэтому не делаем вечный кэш.
- **Независимо от IGDB:** средний балл Rate APP всегда пересчитывается из реальных оценок пользователей; он никогда не берётся из внешнего кэша.

## Политика freshness
По возрасту игры от `first_release_date`:

| Дата релиза относительно текущей даты | TTL |
|---|---:|
| Будущий релиз и первые 30 дней | 7 дней |
| 30–179 дней | 30 дней |
| 180–729 дней | 90 дней |
| 730–1824 дня | 180 дней |
| 1825+ дней | 365 дней |
| Дата неизвестна | 60 дней |

Вычисление: `api/games_routes.py::_game_details_cache_days`. Срок **не запускает сканирование всего каталога**. По открытию деталей:
1. Ссылки/трейлеры/время прохождения отдаются из локальной БД, если ещё свежие; при истечении срока детали запрашиваются заново.
2. Если устарела `games.cached_at`, отправляется низкоприоритетный фоновый запрос *только для открытой игры* с полями рейтинга, количества оценок, обложки, названия, даты, жанров, платформ, ссылок и видео; пользователь не ждёт его ответа.
3. Поля из внешнего поиска также сохраняются немедленно, поэтому ручной поиск в IGDB может обновить запись раньше TTL.
4. При проблемах IGDB старый кэш остаётся доступным; обновление выполняется снова при следующем просмотре после восстановления. `game_time_to_beats` иногда отсутствует в IGDB; для пустых данных не надо делать безусловный запрос по каждому открытию.

Не путать TTL подробностей и обновление общей оценки Rate APP: последняя всегда живая.

## Единый коннектор `api/igdb_client.py`
- Все внешние IGDB вызовы (`games`, `genres`, `search`, `game_time_to_beats`, резерв `multiquery`) проходят через один клиент с кэшированным Twitch OAuth токеном.
- Очередь `PriorityQueue` ограничена 48 запросами на процесс, работник последовательно отправляет запросы. **Приоритеты:** SEARCH (внешний поиск и fallback алиасов), DETAILS (текущий открытый экран), BACKGROUND (жанры и обновление старого кэша).
- Между IGDB-запросами не меньше 0.75 секунды: до ~1.33 запроса/сек на экземпляр FastAPI. Наши два окружения на одном VPS со своими процессами используют одни IGDB credentials, поэтому суммарно в обычном режиме до ~2.67 запросов/сек при предельном ограничении IGDB 4 запросов/сек и 8 одновременных. Не расширять число worker/process без централизованного межпроцессного лимитера.
- Ответ 429: не более двух повторов с ограниченной паузой; 401: один обновлённый токен; временная сеть/формат/очередь возвращают явную ошибку, не зависают бесконечно.
- Очередь **в памяти процесса**, при перезапуске ожидавшие фоновые обновления теряются; это безопасно, поскольку кэш остаётся и повторная попытка произойдёт на следующем запросе. Нет глобального периодического джоба и нет автоматического широкого сбора каталога.
- В будущем, для Tinder, использовать пакетное пополнение *общих кандидатов*, а не IGDB на каждый свайп. `multiquery` поддерживается API, но сам подбор/планировщик здесь **не внедрён**.

## Проверка
Сценарии CI: не меняются PWA, настоящие оценки пользователей, поиск по альтернативным названиям, store URL/trailer, wishlist; отдельные unit-тесты TTL, приоритетов и 429. Сначала `develop` + `https://dev.r-app.ru`; без согласования не продвигать experimental-релиз в `main`.

Ограничение: изменение поля `cached_at` реализуется после успешной IGDB-загрузки; история старых записей сохраняется. Нет отдельной миграции или удаления пользовательских данных.
